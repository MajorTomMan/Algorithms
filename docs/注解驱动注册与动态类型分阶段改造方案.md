# 注解驱动注册与动态类型分阶段改造方案

## 1. 目标

本次改造的目标不是重写算法、结构、Event、Timeline 或 Visualizer，而是重构“组件如何被发现、注册、匹配和实例化”这一层，使 Algorithm / Structure / Practice 后续能够共享同一套固定包内的自动发现机制。

核心目标：

```text
固定包扫描
    ↓
识别框架注解
    ↓
校验接口 / 泛型 / type / structure
    ↓
生成 Descriptor
    ↓
Registry
    ↓
Resolver
    ↓
Runtime
    ↓
现有 Event / Timeline / Reducer / Visualizer
```

明确边界：

- 只支持项目自身固定包内的类。
- 不支持外部 JAR 插件、第三方扩展包、动态 ClassLoader 扩展。
- 第一阶段不引入 Annotation Processor，不生成 META-INF 索引。
- 不把算法实现强制泛型化；Integer/String/Long 算法可以继续分别实现。
- Structure 实现保持泛型复用，例如 `Array<T>`、`LinkedList<T>`、`Tree<T>`、`Graph<T>`。
- `ExecutionEvent / StructureEvent / ObservationEvent` Contract 不因注册系统改造而增加算法特化语义。
- Timeline、Recording、Replay、Statistics 的现有语义保持不变。
- Snapshot 继续保持 UI-neutral，不保存字体/展示偏好。

## 2. 最终注解模型

### 2.1 Structure

结构实现通过注解声明稳定身份和 Contract。

```java
@Structure(
        id = "array",
        contract = ArrayStructure.class
)
public final class Array<T> implements ArrayStructure<T> {
}
```

一个实现允许对应多个逻辑结构 Contract，因此 `@Structure` 应支持重复标注。例如 `LinkedList<T>`：

```java
@Structure(id = "linked-list", contract = LinkedStructure.class)
@Structure(id = "stack", contract = StackStructure.class)
@Structure(id = "queue", contract = QueueStructure.class)
public final class LinkedList<T>
        implements LinkedStructure<T>, StackStructure<T>, QueueStructure<T> {
}
```

注解只声明注册信息，不替代 Java interface。Registry 启动时必须验证 `implementation` 实际实现了声明的 `contract`。

### 2.2 Algorithm

Algorithm 强制声明：

- 稳定 `id`
- 算法处理的运行时值类型 `type`
- 算法要求的结构 Contract `structure`

```java
@Algorithm(
        id = "quick-sort",
        type = Integer.class,
        structure = ArrayStructure.class
)
public final class IntegerQuickSort implements Sort<Integer> {
}
```

String 算法仍然可以使用同一个 Array Structure：

```java
@Algorithm(
        id = "string-sort",
        type = String.class,
        structure = ArrayStructure.class
)
public final class StringSort implements Sort<String> {
}
```

目标关系：

```text
IntegerQuickSort
    type = Integer
    structure = ArrayStructure
            ↓
      Array<Integer>

StringSort
    type = String
    structure = ArrayStructure
            ↓
       Array<String>
```

Algorithm 不直接指定具体实现 `Array.class`，而只指定 `ArrayStructure.class`。具体实现由 `StructureResolver` 选择。

### 2.3 Problem / Practice

Practice 后续使用：

```java
@Problem(
        source = ProblemSource.LEETCODE,
        id = "1",
        title = "两数之和"
)
public final class TwoSum {

    @ProblemEntry
    public static int[] twoSum(int[] nums, int target) {
        ...
    }
}
```

`@ProblemEntry` 只负责声明执行入口，不承担 Trace、Visualizer 或 Event 语义。

第一轮 Algorithm / Structure 注册改造完成前，不实施 Practice UI。

## 3. Descriptor 模型

现有 Registry 的核心问题是把 family、valueType、id 都编码进字符串：

```text
structure.array.Integer
algorithm.array.Integer.quick-sort
```

改造后，字符串 key 不再作为领域信息的主要载体。

建议核心 Descriptor：

```java
public record StructureDescriptor(
        String id,
        Class<?> contract,
        Class<?> implementation
) {
}
```

```java
public record AlgorithmDescriptor(
        String id,
        Class<?> valueType,
        Class<?> structureContract,
        Class<?> implementation
) {
}
```

后续 Practice：

```java
public record ProblemDescriptor(...) {
}
```

Registry 管理 Descriptor，而不是依赖调用方手工拼接：

```text
algorithm.array.Integer.quick-sort
```

这种 key。

---

## 4. 扫描范围

Runtime Discovery 只扫描：

```text
com.majortom.algorithms.structure
com.majortom.algorithms.algorithm
com.majortom.algorithms.practice
```

第一阶段实际只启用前两个包。

不要扫描整个：

```text
com.majortom.algorithms
```

避免 Client、Server、JavaFX Controller 等无关类进入候选集合。

新增统一：

```java
FrameworkClassScanner
```

职责仅为：

```java
List<Class<?>> scan(String rootPackage)
```

Scanner 不理解 Algorithm / Structure / Problem 语义。

上层分别由：

```text
StructureDiscovery
AlgorithmDiscovery
ProblemDiscovery
```

解释注解并生成 Descriptor。

## 5. 注册校验原则

Annotation 不能成为绕过 Java 类型系统的手段。

### Algorithm 必须校验

例如：

```java
@Algorithm(
        id = "foo",
        type = String.class,
        structure = ArrayStructure.class
)
public final class Foo implements Sort<Integer> {
}
```

必须在 Registry 构建阶段直接失败：

```text
annotation type = String
contract type   = Integer
```

同理：

```java
@Algorithm(
        id = "foo",
        type = Integer.class,
        structure = TreeStructure.class
)
public final class Foo implements Sort<Integer> {
}
```

必须拒绝，因为 `Sort<Integer>` 的结构能力与声明的 `TreeStructure` 不一致。

### Structure 必须校验

```java
@Structure(
        id = "array",
        contract = ArrayStructure.class
)
public final class Foo {
}
```

如果 `Foo` 不实现 `ArrayStructure`，直接拒绝注册。

### 其他约束

- `id` 必须唯一。
- Algorithm `id` 使用稳定 kebab-case。
- concrete component 不允许 abstract / interface。
- Algorithm `type` 优先使用包装类型，例如 `Integer.class`、`Long.class`，不使用 `int.class`、`long.class`。
- implementation 必须满足框架可实例化条件。
- 冲突、无法解析、类型不一致全部 fail-fast，不静默覆盖。

# 6. 分阶段实施

## Phase 0：基线锁定与映射清单

### 目标

在任何代码重构前确认现有 Registry 能力集合，并给每一个现有 Structure / Algorithm 建立目标注解映射。

### 工作

1. 导出现有 Structure registrations。
2. 导出现有 Algorithm registrations。
3. 记录现有 Workbench 可见算法集合。
4. 为每个 Algorithm 明确：
   - `id`
   - `type`
   - `structure`
5. 为每个 Structure 明确：
   - `id`
   - `contract`
   - `implementation`
6. 保留当前 Quick Sort / Graph BFS / KMP / Maze probe 作为迁移对照。

### 特别决策点：Maze

当前 Array Maze 使用 `GridMaze` 领域对象，而不是普通 `ArrayStructure<T>` Contract。

在进入 Phase 1 前必须明确 Maze 注解如何表达 `structure`：

方案只能二选一，不允许 Discovery 中写隐式特殊分支：

```text
A. 将 GridMaze 明确纳入可注册 Structure/Domain Structure；
B. 新增明确的 Maze Structure Contract，并让 GridMaze 对应它。
```

该问题必须先确定，否则“Algorithm 必须指定 structure”的规则无法对所有现有算法保持一致。

### 验收

```text
迁移前 registry snapshot 已保存
所有现有 concrete algorithm 都有明确注解映射
所有现有 structure 都有明确注解映射
Maze structure contract 决策完成
```

## Phase 1：Annotation + Descriptor 基础层

### 新增

建议新增：

```text
core/annotation/
  Algorithm.java
  Structure.java
  Structures.java

core/registry/
  AlgorithmDescriptor.java
  StructureDescriptor.java
  RegistrationException.java
  RegistrationValidator.java
```

如果不希望 `core` 直接依赖 algorithms / structures 的具体 contract，则 Annotation 与通用 Descriptor 只使用 `Class<?>`，具体 contract 校验放 Discovery 层完成。

### 本阶段禁止

- 不改 Client UI。
- 不删除现有 factories。
- 不删除旧 ModuleRegistry。
- 不改算法实现逻辑。
- 不改 StructureEvent。

### 验收

Annotation/Descriptor 单元测试通过，并覆盖：

```text
合法声明
重复 ID
空 ID
contract 不匹配
algorithm type 不匹配
algorithm structure 不匹配
```

---

## Phase 2：固定包 Scanner + Annotation Discovery

### 新增

```text
FrameworkClassScanner
StructureDiscovery
AlgorithmDiscovery
```

Scanner 只扫描固定根包。

Discovery 输出 Descriptor，不再输出拼接后的 registry key。

### 迁移策略

本阶段暂时“双轨运行”：

```text
旧 ModuleLoader / factories
        +
新 Annotation Discovery
```

测试时比较二者结果，而不是立即删除旧系统。

### 对现有实现加注解

Structure 约 7 个实现类。

Algorithm 约 14～18 个 concrete implementation。

算法内部实现不改，只加 metadata。

### 验收

必须满足：

```text
旧注册集合 == 新注解注册集合
Algorithm ID 不变化
Structure 可用能力不减少
Quick Sort probe 通过
Graph BFS probe 通过
KMP probe 通过
Maze probe 通过
```

---

## Phase 3：Descriptor Registry + StructureResolver

### 目标

让 Runtime 不再依赖：

```text
structure.array.Integer
algorithm.array.Integer.quick-sort
```

这种字符串拼接规则。

### 新增/重构

```text
ComponentRegistry
StructureResolver
```

典型执行流程：

```text
algorithmId
    ↓
AlgorithmDescriptor
    ↓
valueType = String.class
structureContract = ArrayStructure.class
    ↓
StructureResolver
    ↓
StructureDescriptor
    ↓
Array.class
```

### Structure 泛型复用

Registry 不再为同一个泛型实现维护：

```text
structure.array.Integer
structure.array.Long
structure.array.String
```

三份重复 registration。

而是：

```text
StructureDescriptor(array, ArrayStructure.class, Array.class)
```

运行实例另行携带：

```text
valueType = Integer/String/Long
```

### 验收

- Resolver 能根据 AlgorithmDescriptor 找到兼容 Structure。
- 同一个 `Array.class` 能分别建立 Integer/String/Long runtime context。
- 类型不兼容 fail-fast。
- Registry 查询 API 不要求调用方拼 registry key。

---

## Phase 4：切换正式注册源，删除旧 factories/discovery

### 删除/退出

在 Phase 2、3 全部验证通过后，删除：

```text
structures/src/main/resources/META-INF/algorithms.factories
algorithms/src/main/resources/META-INF/algorithms.factories
旧 AlgorithmModuleDiscovery 的类名推 ID 逻辑
旧 ModuleDiscovery ServiceLoader 注册路径（若已无其他用途）
```

是否完全删除 `ModuleRegistry / ModuleLoader` 取决于迁移后的 API 复用程度；不要为了命名一次性大改所有调用方，可以先做兼容 facade，再在本阶段末移除。

### 验收

- 项目启动只依赖 Annotation Discovery。
- 无 factories 仍能得到完整 Structure/Algorithm catalog。
- 无 class-name-derived algorithm id。
- 重命名 algorithm implementation class 不改变稳定 ID。

---

## Phase 5：Client 从字符串 key 切换到 Descriptor

### 主要涉及

```text
MainController
BaseController
AlgorithmCatalog
WorkbenchModules
ArrayController
LinkedListController
LinearStructureController
TreeController
GraphController
StringController
MazeController
```

### 修改方向

禁止继续：

```java
module("algorithm.array.Integer." + algorithmId, Sort.class)
```

改为：

```text
algorithmId
  ↓
AlgorithmDescriptor
  ↓
Registry.createAlgorithm(...)
```

Structure 同理。

### 本阶段可以继续只显示 Integer

本阶段重点是移除“字符串 registry key”依赖，不要求马上完成所有 ViewState 的动态类型显示。

### 验收

- Workbench 所有现有功能与迁移前一致。
- Snapshot / Inspector / Timeline / Replay 无回归。
- Algorithm selector 来自 Descriptor Registry。
- Controller 中不再出现 `algorithm.array.Integer.` 等硬编码拼接。

## Phase 6：ValueType 动态化 POC —— 只做 Array

### 目标

先证明最终目标：

```text
同一个 Array<T>
同一个 Array Visualizer
不同类型算法
```

先只做两种类型：

```text
Integer
String
```

不要一开始推广到所有结构。

### 需要修改

当前 `ArrayViewState`、Array Controller、输入解析、随机/示例数据和展示层仍然存在 Integer 假设。

建议新增统一值展示层：

```java
public record VisualValue(
        Object value,
        String text
) {
}
```

或等价的 `ValueFormatter` 方案。

Visualizer 只关心：

```text
index
text
mutation
observation
```

而不关心值是 Integer 还是 String。

### POC 必须新增一个 String + ArrayStructure 算法

例如：

```java
@Algorithm(
        id = "string-sort-test",
        type = String.class,
        structure = ArrayStructure.class
)
```

只用于验证 Framework 兼容模型，不要求成为最终正式算法。

### 验收

```text
Integer Array algorithm 正常
String Array algorithm 正常
两者复用同一个 Array<T>
两者复用同一个 Array Reducer/Visualizer
Timeline 可正常 replay
Snapshot 输入可恢复
```

此阶段通过后，才允许推广动态 ValueType。

---

## Phase 7：推广动态 ValueType 到 Linked / Tree / Graph

### 范围

逐个处理：

```text
LinkedListViewState
TreeViewState
GraphViewState
对应 Reducer
对应 Visualizer
对应 Controller
```

不要把 JavaFX Controller 泛型化到底。

优先选择：

```text
Object/VisualValue + Formatter
```

而不是让：

```text
Controller<T>
ViewState<T>
Visualizer<T>
```

在 UI 层大面积传播泛型。

### 验收

每个 family 至少有 Integer + 第二类型 smoke test。

结构拓扑语义必须保持不变：

```text
Array      index
Linked     next/previous
Tree       parent/children/left/right
Graph      vertex/edge
```

只泛化 value type，不制造 UniversalStructure。

---

## Phase 8：Server Registry API 迁移

Server 当前仍有显式 Algorithm API Descriptor 和旧 registry key。

第一轮只做 Registry API 迁移：

```text
旧 String registry key
    ↓
AlgorithmDescriptor / ComponentRegistry
```

暂不做动态 REST request schema。

如果未来 Server 需要同时接受 Integer/String/Long，再单独设计：

```text
ValueCodec
request validation
serialization
API schema
```

这不属于本轮 Annotation Registry 核心改造。

---

## Phase 9：Practice / LeetCode 接入

只有 Algorithm / Structure 新 Registry 稳定后才开始。

新增：

```text
@Problem
@ProblemEntry
ProblemDescriptor
ProblemDiscovery
PracticeProblemRegistry（或并入 ComponentRegistry）
Practice Runner
```

Practice 使用同一个：

```text
FrameworkClassScanner
Descriptor
Registry
ValueType
StructureResolver
```

但不会强迫普通 LeetCode 方法实现正式 Algorithm interface。

后续执行可视化仍按已验证方向：

```text
Practice Worker JVM
        ↓
真实执行
        ↓
JDI Source Trace + Structure Facts
        ↓
immutable recording
        ↓
程序结束
        ↓
Workbench Replay
        ↓
左 Code + 右现有 Structure Visualizer
```

代码错误形成的错误结构必须忠实保存并回放，不预测、不纠正程序。

# 7. 明确不做的事情

本次改造不做：

- 外部 JAR / Plugin SPI。
- Annotation Processor / generated index。
- Spring/DI Container。
- `@Inject` / `@Component` 式对象生命周期管理。
- 将 Algorithm 强制泛型化。
- UniversalStructure/ObjectGraph 统一所有结构。
- Event Contract 算法特化。
- 在 Annotation 中描述 Visualizer、Reducer、Snapshot、I18N label。
- 在 Annotation 中塞测试数据。
- 为了兼容旧 key 长期保留双注册体系。

# 8. 预计改动规模

完整做到 Phase 8，当前估计：

```text
核心 Registry / Discovery       8～12 个文件

Algorithm 注解迁移             14～18 个文件
Client Registry 消费             7～10 个文件
Client ValueType 泛化           10～16 个文件
Server                           1～4 个文件
Tests / Docs                     8～12 个文件
```

存在文件重叠，预计最终约：

```text
35～50 个 Java 文件发生有效修改
8～12 个新的框架类
删除/替换 3～4 个旧注册/Discovery 资源
约 2000～3500 行有效 diff（包含删除和测试）
```

风险等级：中。

风险主要集中在 Client 中已有的 Integer 假设，而不是 Structure/Event/Timeline 核心。

# 9. 推荐执行顺序

严格按以下顺序实施：

```text
Phase 0  基线与映射
   ↓
Phase 1  Annotation + Descriptor
   ↓
Phase 2  Fixed Package Discovery
   ↓
Phase 3  Registry + Resolver
   ↓
Phase 4  删除 factories / old discovery
   ↓
Phase 5  Client 切 Descriptor API
   ↓
Phase 6  Array<Integer/String> POC
   ↓
Phase 7  推广 Linked/Tree/Graph
   ↓
Phase 8  Server API 迁移
   ↓
Phase 9  Practice / LeetCode
```

每个阶段都必须保持项目可编译、现有 Probe 可运行，不允许跨多个 Phase 后再一次性修复。

# 10. 最终架构目标

```text
                     Fixed Package Scanner
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
     @Structure          @Algorithm          @Problem
          │                   │                   │
          ▼                   ▼                   ▼
 StructureDiscovery   AlgorithmDiscovery   ProblemDiscovery
          │                   │                   │
          └───────────────────┼───────────────────┘
                              ▼
                      Descriptor Registry
                              │
                              ▼
                           Resolver
                              │
                  ┌───────────┴───────────┐
                  ▼                       ▼
          Structure Instance        Algorithm/Problem
                  │                       │
                  └───────────┬───────────┘
                              ▼
                            Runtime
                              │
                              ▼
             StructureEvent / ObservationEvent
                              │
                              ▼
                   Timeline / Recording
                              │
                              ▼
                    Reducer / ViewState
                              │
                              ▼
                         Visualizer
```

最终原则：

> Annotation 负责声明身份与兼容信息；Interface 负责行为契约；Descriptor 保存运行时 metadata；Resolver 负责匹配具体结构实现；Event/Timeline/Visualizer 继续只表达真实执行事实和结构状态。
