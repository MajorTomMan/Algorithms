# 服务器长期实现维护文档

本文档是 `server` 模块的长期实现清单。它描述服务端要逐步具备的功能、需求边界、接口路径和验收标准，不代表这些 HTTP 接口已经全部实现。

当前 `server` 只有 Spring Boot 启动类，算法目录和具体算法实现位于 `algorithms`，公共执行协议位于 `core`。服务端不依赖 `client`，不使用 JavaFX、FXML、GraphStream JavaFX 渲染器或客户端样式。

## 总体目标

将内置算法包装成一个可以被网页或其他客户端使用的算法执行服务：

```text
HTTP 请求
    ↓
server API / DTO / 校验
    ↓
AlgorithmCatalog + InputCodec
    ↓
ExecutionSession + DefaultAlgorithmRunner
    ↓
ExecutionEvent + ExecutionStatistics
    ↓
SSE / 查询接口 / 结果记录
```

服务端只负责目录、输入、执行、会话、事件和资源治理。浏览器中的颜色、布局、动画插值和视图状态由网页客户端负责；JavaFX 客户端也不应成为服务器依赖。

## 实现原则

1. 只允许执行明确注册在 `ProviderCatalog` 中的算法，不接受类名、包名或任意反射入口。
2. 每次执行创建独立的算法实例、运行控制、事件记录和结果，不共享可变算法对象。
3. 算法事件先进入服务端权威记录，再向 SSE 等观察者广播。
4. 慢客户端不能阻塞算法线程；广播队列必须有界，并定义丢弃、合并或断开策略。
5. 所有输入、事件数、运行时间、并发数和输出都要有服务器侧限制。
6. 命令接口需要幂等；重复的暂停、恢复、取消请求不能破坏运行状态。
7. API DTO 与 `core` 领域对象分离。不能直接把 GraphStream 对象、Java 类名或内部实现细节作为网络协议。
8. 先完成内置算法服务化，再考虑在线写代码、编译和沙箱运行。

## 阶段目标

### 阶段一：服务端骨架和目录查询

目标：让服务端可以独立启动，并返回可供前端选择的算法目录。

需要完成：

- `server/pom.xml` 增加 `algorithms-library` 依赖。
- 增加目录服务，将 `ProviderCatalog.production()` 转换为服务端 DTO。
- 为算法 ID、模块、版本、输入类型和输出类型建立稳定的响应字段。
- 增加统一异常处理、参数校验和健康检查。

候选接口：

```text
GET /api/v1/health
GET /api/v1/algorithms
GET /api/v1/algorithms/{algorithmId}
```

目录响应示例：

```json
{
  "id": "quick-sort",
  "moduleId": "sort",
  "version": "2.0",
  "inputType": "IntegerSortInput",
  "outputType": "IntegerSortOutput",
  "capabilities": ["events", "statistics"]
}
```

验收标准：

- 未知算法 ID 返回明确的 404 或业务错误。
- 目录 ID 唯一且顺序稳定。
- server 编译和启动不需要 JavaFX 环境。

### 阶段二：输入编解码和同步执行内核

目标：先在不引入 HTTP 长连接的情况下，打通一次完整执行。

需要完成：

- `AlgorithmInputCodec`：将请求 JSON 转换为指定的 `AlgorithmInput`。
- `AlgorithmOutputCodec`：将 `AlgorithmOutput` 转换为稳定 JSON。
- 输入规模和字段校验。
- `ExecutionService`：选择 Provider、准备输入、调用 `DefaultAlgorithmRunner`、收集结果。
- 事件记录和 `ExecutionStatistics` 归约。

建议的内部接口：

```text
AlgorithmInputCodec<I extends AlgorithmInput>
AlgorithmOutputCodec<O extends AlgorithmOutput>
AlgorithmInputCodecRegistry
ExecutionService
```

第一批应优先支持排序和数组迷宫，再接入 AVL、图 BFS、图迷宫生成。输入 JSON 必须采用白名单映射，不能把 Jackson 反序列化目标交给客户端控制。

### 阶段三：异步执行会话

目标：HTTP 请求只负责创建任务，算法在专用有界线程池中运行。

每个执行会话至少保存：

```text
runId
algorithmId
status
input summary
future
RunControl
event store
result
statistics
createdAt / startedAt / endedAt
```

建议状态：

```text
CREATED → QUEUED → RUNNING ⇄ PAUSED
                         ↓
       SUCCEEDED / FAILED / CANCELLED / TIMED_OUT / EXPIRED
```

建议接口：

```text
POST   /api/v1/runs
GET    /api/v1/runs/{runId}
GET    /api/v1/runs/{runId}/result
GET    /api/v1/runs/{runId}/events
DELETE /api/v1/runs/{runId}
```

创建执行示例：

```json
{
  "algorithmId": "quick-sort",
  "input": {
    "values": [5, 2, 8, 1]
  }
}
```

响应示例：

```json
{
  "runId": "run-uuid",
  "algorithmId": "quick-sort",
  "status": "QUEUED",
  "eventsUrl": "/api/v1/runs/run-uuid/events"
}
```

算法执行不得运行在 Spring MVC 请求线程中。使用有界 `ThreadPoolExecutor`，并为队列满、拒绝执行和超时定义明确错误。

### 阶段四：实时事件和回放

目标：网页可以实时看到算法执行，并在断线后继续读取记录。

MVP 使用 SSE：

```text
GET /api/v1/runs/{runId}/events
```

每条 SSE 事件建议包含：

```json
{
  "protocolVersion": 1,
  "runId": "run-uuid",
  "sequence": 12,
  "type": "algorithm",
  "occurredAt": "2026-08-13T10:20:30Z",
  "payload": {
    "eventType": "SortSwappedEvent",
    "leftIndex": 1,
    "rightIndex": 3
  }
}
```

事件类型至少包括：

```text
state
algorithm
statistics
completed
cancelled
failed
heartbeat
```

要求：

- 使用 `sequence` 保证事件顺序。
- 支持 `Last-Event-ID` 断线续传。
- 权威事件记录与 SSE 广播解耦。
- 慢连接使用有界队列，不能让算法线程无限等待浏览器。
- 事件记录需要按 run 分页或分段读取，不能无限堆积在单个内存 List 中。

### 阶段五：暂停、恢复和取消

目标：将 `core` 中的 `RunControl` 暴露为幂等的服务端命令。

接口：

```text
POST /api/v1/runs/{runId}/commands
```

请求示例：

```json
{
  "commandId": "command-uuid",
  "type": "PAUSE"
}
```

支持命令：

```text
PAUSE
RESUME
CANCEL
```

后续可以增加：

```text
STEP
SPEED
```

但 `STEP` 只能对使用协作式 checkpoint 的算法承诺；任意不检查取消状态的代码不能保证安全暂停。命令处理必须检查当前状态，使用 `commandId` 做幂等去重，并返回新的状态和状态版本号。

### 阶段六：限制、清理和可观测性

目标：让服务端在多个执行同时存在时仍然可控。

至少需要配置：

```text
最大并发执行数
最大排队任务数
单次最大输入规模
单次最大事件数
单次最大运行时间
单次最大输出大小
事件保留时间
```

建议初始保护值：

```text
排序元素：10,000
迷宫单元格：100,000
图节点：10,000
单次事件：200,000
单次运行：30 秒
```

这些只是服务端默认值，必须通过配置集中管理；客户端提交的限制只能更严格，不能扩大服务器上限。

可观测性至少包括：

- 当前运行数、队列长度和拒绝数。
- 每个算法的执行次数、成功率、取消数和失败数。
- 事件吞吐量、SSE 连接数和慢客户端数。
- 执行耗时、事件数量和输出大小。
- 结构化日志中的 `runId`、`algorithmId` 和错误码。

### 阶段七：持久化、多用户和安全

目标：从单机内存原型发展为可恢复的服务。

建议拆分：

```text
数据库：用户、权限、运行元数据、状态
对象存储：输入、输出、事件段、checkpoint
消息系统：任务队列和实时广播
```

安全要求：

- 鉴权和对象级权限检查。
- 运行 ID 不可预测，防止越权读取其他 run。
- 请求体、数组、图和迷宫尺寸严格限制。
- CORS 使用明确白名单。
- 日志不得泄露令牌、完整源码或敏感输入。
- 服务端不加载客户端类，不接受任意类名执行。

## 在线输入代码的后续路线

在线输入代码、即时编译和可视化不是普通的 REST 功能，建议独立为后续阶段：

```text
Workspace
  → Revision
  → Build
  → BuildDiagnostics
  → Run
  → Worker
  → EventStream
```

第一版只开放 `ProviderCatalog` 中的内置算法。开放用户代码后，编译和运行都必须放在独立 worker 或容器中，限制 CPU、内存、线程、文件和网络；不能在 Spring Boot JVM 内通过 `JavaCompiler + ClassLoader` 直接加载不可信代码。

## 推荐 server 包结构

```text
server/src/main/java/.../server/
├── api/              Controller、请求/响应 DTO、SSE
├── application/      目录、执行、命令服务
├── codec/            Input/Output 编解码和白名单注册表
├── runtime/          会话、线程池、事件存储、广播
├── config/           线程池、限额、CORS、序列化配置
├── error/            统一异常和错误码
└── observability/    指标、日志和健康检查
```

服务端不应出现以下依赖：

```text
JavaFX Controller
FXML
GraphStream JavaFX renderer
client reducer
AlgorithmLabels
客户端 CSS
```

## 第一版 MVP 验收清单

- [ ] server 可以独立启动，不需要 JavaFX。
- [ ] server 依赖 `core` 和 `algorithms`，不依赖 `client`。
- [ ] 可以查询内置算法目录。
- [ ] 可以提交排序或迷宫执行任务并获得 `runId`。
- [ ] 算法在后台有界线程池执行。
- [ ] 可以查询运行状态、结果和统计。
- [ ] SSE 能接收有序事件。
- [ ] 支持取消；暂停和恢复随后补齐。
- [ ] 多个 run 互不影响。
- [ ] 输入、并发、事件数和超时限制有效。
- [ ] API、状态机和 SSE 有契约测试。

## 常用开发命令

在仓库根目录执行：

```bash
# 安装 server 及其 reactor 依赖
mvn -pl server -am install -DskipTests

# 启动 Spring Boot
mvn -f server/pom.xml spring-boot:run

# 验证 server 及其依赖
mvn -pl server -am test

# 验证整个 reactor
mvn clean verify
```

当前构建产物是普通 Maven JAR；除非后续显式配置 Spring Boot `repackage`，不要用 `java -jar` 作为 server 的启动方式。
