# 服务器长期实现维护文档

本文档描述服务器的长期目标和实现顺序。项目定位是“数据结构实验与算法步骤可视化”，不是判题平台。

用户选择一种数据结构，准备一份受限制的输入，编写适用于该数据结构的算法，服务器执行算法并输出每一步事件、最终结果和统计数据。网页或 JavaFX 负责播放事件，服务器不负责界面布局和颜色。

## 一、总体边界

```text
JavaFX 客户端 ─┐
                ├─ core：执行接口、领域事件、回放、统计
网页客户端 ────┘
                ↑
            server：会话、任务、协议、权限、资源限制
```

- `core` 保存客户端和服务器都能理解的执行模型。
- `client` 负责 JavaFX 控件、`EventReducer`、ViewState、动画和本地执行。
- `server` 负责 HTTP、执行会话、事件传输、输入限制、存储和安全。
- `algorithms` 先作为内置示例和演示算法使用，服务器第一阶段可以只依赖 `core`。
- 服务器不能依赖 JavaFX、FXML、GraphStream UI 类或客户端的 reducer。
- 用户代码不能直接加载到 Spring Boot 主进程中。

## 二、当前基础

目前 `core` 已具备以下公共能力：

- `Algorithm`、`AlgorithmProvider`、`AlgorithmContext` 等执行扩展接口；
- 强类型输入、输出和领域事件；
- `EventReducer` 和 `ReductionCursor`，用于把事件恢复为可播放状态；
- 执行生命周期、取消、暂停、单步和事件记录；
- `ExecutionSummary`、`ExecutionStatistics`、`ExecutionTiming` 和 `ResourceUsage`；
- `RecordingEventSink`，可保存事件并生成最终摘要。

JavaFX 使用同一套执行事件和统计对象，只是在本地增加 JavaFX 的节拍器、播放控制和绘制器。服务器以后可以把这些对象转换为 HTTP DTO，不需要复制一套统计规则。

当前 server 是原型，已有健康检查、算法查询和执行查询入口，但执行闭环、事件持久化、异步会话和安全限制仍需完善。`HealthServiceImpl` 中的执行顺序也需要先运行并完成记录，再读取 recording snapshot；这属于服务器实现阶段的首要修复项。

## 三、产品模型：按数据结构组织

服务器目录不应以固定算法列表作为主要入口，而应以数据结构分类：

- 数组、线性表；
- 树；
- 图；
- 数组迷宫或网格；
- 后续再增加栈、队列、堆、链表等结构。

每种结构需要提供：

1. 结构说明和可视化类型；
2. 输入字段及校验规则；
3. 有限的预设数据；
4. 有限的自定义数据范围；
5. 允许发出的事件类型；
6. 对应的 reducer 或事件解释规则；
7. 默认运行、事件和资源上限。

示例输入范围：

```text
数组：5、10、20、50、100 个元素
树：7、15、31 个节点
图：5、10、20 个节点，限制边数和权重范围
迷宫：11×11、21×21、31×31
```

用户可以在这些范围内选择预设或输入数据，但不能通过请求放宽服务器限制。

服务器不需要猜测用户每一行代码做了什么。算法必须通过 SDK 显式发出 `compare`、`swap`、`visitNode`、`rotate`、`backtrack`、`checkpoint` 等有意义的事件，才能保证逐帧可视化。没有显式事件的程序，只能提供输出、错误和退出状态。

## 四、阶段一：修复执行原型

### 目的

先保证一次执行可以可靠地开始、结束、失败、取消，并且结果和事件记录完整。

### 工作内容

- 每次请求创建独立的 runId、算法实例、输入和事件记录；
- 先运行 `DefaultAlgorithmRunner`，再读取 `RecordingEventSink` 的 snapshot；
- 保存输出、事件、统计、资源摘要和失败原因；
- 统一 `QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`TIMED_OUT` 等状态；
- 处理未知结构、输入错误、队列拒绝和执行异常；
- 不允许一个任务覆盖另一个任务的状态。

### 完成标准

合法输入能得到完整结果和终态；非法输入不会创建任务；算法异常不会让任务永久停在 `RUNNING`；同一事件序列可以恢复出与结果一致的状态。

## 五、阶段二：结构目录和输入配置

### 目的

让网页先了解“可以实验哪些数据结构、如何准备输入”，再提交运行任务。

### 目标接口

```text
GET /api/v1/structures
GET /api/v1/structures/{structureType}
```

返回内容至少包括：

```text
structureType、name、description、inputSchema
presets、customLimits、eventSchema、rendererKind
defaultLimits、capabilities
```

这里的目录是数据结构目录，不是允许用户调用的 Java 类名列表。服务器必须用白名单和显式注册信息构造目录。

## 六、阶段三：运行会话

### 目的

把一次算法执行变成可查询、可控制的会话，而不是占用 HTTP 请求直到算法结束。

### 目标接口

```text
POST   /api/v1/runs
GET    /api/v1/runs/{runId}
GET    /api/v1/runs/{runId}/record
DELETE /api/v1/runs/{runId}
```

创建请求可以采用以下形式：

```json
{
  "structureType": "array",
  "input": {"values": [5, 2, 8, 1]},
  "source": {"type": "builtin", "id": "example"},
  "requestedLimits": {"maxEvents": 10000}
}
```

以后支持用户代码时，`source` 再增加不可变的 revision 或 buildArtifact 引用。不要直接运行一个可变工作区。

会话至少保存：

```text
runId、structureType、sourceRef、status、stateVersion
inputSummary、output、failure、statistics、resources
createdAt、startedAt、endedAt、eventStore
```

创建接口返回 `202 Accepted` 和 runId。执行任务放在有界线程池或独立 worker 中，队列满时返回明确的容量错误。

## 七、阶段四：事件流和逐帧回放

### 目的

让网页实时看到算法过程，并让实时观看、断线恢复和之后回放使用同一份权威事件记录。

### 目标接口

```text
GET /api/v1/runs/{runId}/events
GET /api/v1/runs/{runId}/events?fromSequence=100
GET /api/v1/runs/{runId}/checkpoints/{sequence}
```

第一版使用 SSE 即可。事件外层应包含：

```json
{
  "protocolVersion": 1,
  "runId": "run-xxx",
  "sequence": 12,
  "occurredAt": "2026-08-20T10:00:00Z",
  "type": "sort.swapped",
  "payload": {"leftIndex": 1, "rightIndex": 3}
}
```

算法只产生领域事件，runId、sequence、时间和状态由运行时封装。网络 JSON 使用稳定的字符串类型，不暴露 Java 全限定类名。

事件链路：

```text
算法事件 -> 权威 EventStore -> 查询、回放、SSE
                         └-> 观察者
```

观察者不能阻塞算法线程。事件记录需要有界容量、checkpoint、心跳和慢客户端策略。网页断线后使用 `Last-Event-ID` 或 `fromSequence` 继续读取；过期序号需要返回可用 checkpoint，而不是静默丢失。

## 八、阶段五：暂停、恢复、取消和单步

### 目的

把执行控制能力暴露给网页，同时明确算法的真实能力边界。

### 目标接口

```text
POST /api/v1/runs/{runId}/commands
```

请求示例：

```json
{
  "commandId": "cmd-001",
  "expectedStateVersion": 4,
  "type": "PAUSE"
}
```

支持 `PAUSE`、`RESUME`、`STEP`、`CANCEL`。命令必须幂等，重复提交不能重复产生副作用。

- `CANCEL` 必须唤醒被暂停的任务；
- `PAUSE` 只对主动调用 checkpoint 的算法承诺；
- `STEP` 只对定义了单步边界的算法承诺；
- 播放速度属于客户端播放控制，不应偷偷改变算法结果；
- 非协作的无限循环最终只能依靠 worker 超时和外部终止。

## 九、阶段六：统计和资源信息

### 目的

执行结束后给出统一的操作次数、时间和资源消耗。JavaFX 与服务器都使用同一套统计模型。

摘要建议包含：

```text
AlgorithmStatistics
  eventCount、frameCount、inputSize、operationCounts

ExecutionTiming
  eventSpan、totalDuration、playbackDuration

ResourceUsage
  cpuTimeNanos、peakMemoryBytes、outputBytes
```

字段语义：

- `eventSpan` 是事件时间戳跨度，可能包含事件投递和节拍等待；
- `totalDuration` 是宿主执行任务的耗时；
- `playbackDuration` 是客户端回放耗时；
- CPU 时间和峰值内存属于采样结果，必须标明采样来源和是否可用。

JavaFX 使用本地 `ResourceSampler`。服务器在 worker 或容器侧采集资源，再将结果转换为 HTTP DTO。JavaFX 内部不需要 JSON；JSON 只出现在文件导出或网络边界。

## 十、阶段七：限制、存储和故障恢复

### 目的

避免大输入、大量事件或多个用户同时执行导致服务不可用。

至少限制：

```text
请求体、数组、树、图、迷宫的规模
单次事件数、事件总字节数和输出大小
单次运行时间、并发数和排队数
日志大小、事件保留时间和单用户配额
```

单机原型可以使用内存或本地文件，但要提前隔离存储接口。长期可以拆分为：

```text
数据库：用户、权限、结构目录、revision、run 元数据和状态
对象存储：输入、输出、事件段和 checkpoint
消息系统：任务派发、worker 心跳和实时通知
```

需要定义 worker 断开、进程重启、任务重试、事件重复和过期数据清理规则。状态转换应带 `stateVersion`，避免并发命令覆盖状态。

## 十一、阶段八：在线编写算法

### 目的

在内置示例和事件协议稳定后，允许用户修改算法逻辑并再次运行。

### 推荐链路

```text
Workspace -> Revision -> Build -> BuildDiagnostics -> Run -> EventStream
```

第一版限制语言、入口、SDK 版本和依赖范围。源码、revision 和构建产物都应不可变并可追踪。

编译和运行必须放在独立 worker 或 sandbox 中，限制 CPU、内存、线程、文件、网络和运行时间。不能在 Spring Boot JVM 中用 `JavaCompiler + ClassLoader` 直接加载不可信代码。

用户代码只有显式调用 SDK 的 `emit` 或 `checkpoint`，服务器才能承诺逐帧可视化。没有事件的代码只返回标准输出、标准错误和退出状态。

## 十二、阶段九：鉴权和部署

多人使用前需要加入：

- 登录认证、对象级权限和用户配额；
- 不可枚举的 runId、请求限流和审计日志；
- 严格的 JSON、路径、文件和依赖校验；
- worker 与控制面分离，worker 默认无公网入站；
- rootless、只读根文件系统、临时工作区、CPU/内存/pids 配额；
- 超时时终止整个进程组，并清理事件、日志和临时文件。

## 十三、版本、测试和上线标准

接口使用显式版本，例如 `/api/v1`、`/api/v2`。已经发布的字段不能改变含义，事件语义变化应升级协议版本。

每增加一种数据结构，至少完成：

1. 输入 schema 和规模限制；
2. 领域事件及顺序约定；
3. server 侧输入/输出转换；
4. client 或网页侧 `EventReducer` 和可视化；
5. 结果、统计、取消、终态和事件回放验证；
6. 文档和目录更新。

上线前重点验证：多任务隔离、事件序号、断线续传、慢客户端、重复命令、超时、队列满、资源限制、权限校验和 worker 崩溃恢复。

## 十四、常用命令

```bash
# 全部测试和验证
mvn test
mvn clean verify

# 验证 server 及其依赖
mvn -pl server -am test

# 启动 Spring Boot 开发服务
mvn -f server/pom.xml spring-boot:run

# 打包
mvn -pl server -am package
mvn package
```

当前 server 的 jar 是普通构建产物，是否制作可直接 `java -jar` 的可执行包，等服务器实现稳定后再决定，不在本文档中假设。

整体模块关系见[系统架构设计文档](系统架构设计文档.md)。
