# Algorithms V2 Server 维护文档

## 当前职责

Server 是 core + algorithms 的 headless 宿主，不拥有另一套算法架构。

```text
HTTP Request
   ↓
AlgorithmsController
   ↓
AlgorithmExecutionService
   ↓
ModuleRegistry -> concrete domain implementation
   ↓
ExecutionScheduler
   ↓
ExecutionRuntime
   ↓
RecordingEventSink / ExecutionUnit
```

## API

```text
GET  /api/v1/health
GET  /api/v1/algorithms
POST /api/v1/executions
GET  /api/v1/executions/{runId}
```

`POST /executions` 返回 runId；调用方使用该 ID 查询状态。

## 边界规则

- 不接受客户端传入任意 Java 类名。
- algorithmId 只映射到 ModuleRegistry 中允许的资源 key。
- HTTP Request/Response DTO 只属于 server transport 边界，不进入 core/algorithms。
- `algorithms` 不维护 `AlgorithmInput / AlgorithmOutput / XxxInput / XxxOutput`。
- DTO 转换完成后直接调用真实领域方法。
- Server 不依赖 client reducer、ViewState、JavaFX 或 playback。
- 执行线程只通过 core ExecutionScheduler 创建。

## 执行记录

一次执行的权威信息来自 EventEnvelope 流与 Runtime Result：

- runId
- operationId
- status
- total/domain/lifecycle event count
- event span
- Runtime total duration
- domain metrics

playbackDuration 和 visualFrameCount 是 Client presentation 数据，Server 不保存。

## Algorithm I/O 边界

```text
HTTP JSON
   ↓
Server Request DTO
   ↓
Structure / 普通 Java 参数
   ↓
Algorithm
   ↓
真实 Java 返回值
```

`ExecutionRequest`、`core.runtime.ExecutionResult`、`core.snapshot.*` 是独立边界对象，正常保留；它们不能反向要求 algorithms 创建 Input/Output wrapper。

## 新增算法 API

1. 先在 algorithms 用自然 Java 方法签名实现并通过资源文件注册。
2. 如果 HTTP JSON 不能直接表达领域输入，增加窄 DTO。
3. `prepareExecution` 中将 DTO 构造成真实领域输入/结构。
4. 通过 Registry 取得实现。
5. 将领域方法作为 ExecutionOperation 交给 Runtime。

不要增加 Provider、Invoker、反射 class name 或第二套 Runner。

## 并发

Server 使用 bounded ExecutionScheduler。一个 Run 的事件顺序必须保持串行；多个 Run 可以并发。

如果后续增加持久化，应持久化 EventEnvelope/ExecutionRecording，不要把 client ViewState 当服务端历史格式。
