# ALG 框架简化审查

本次范围：核对 `core`、`structures`、`algorithms`、`telemetry`
以及 `client` 的主要类型组织，重点复查渲染、执行、注册表、输入与指标设计。
审查不以“只有一个实现”为删除标准，而以**是否承载独立职责或必须隔离的边界**为判断依据。
本次仅落地可以保持行为不变、能通过现有回归验证的收敛。

## 已落实的简化

| 旧设计 | 发现 | 新设计 |
|---|---|---|
| `RenderSessionRegistry` | 只有一个使用方，三个方法仅转发 `Map` | 直接由 `DefaultRenderFramework` 持有 `LinkedHashMap<RenderSessionId, RenderSession>`，私有 `session(id)` 统一 `computeIfAbsent` |
| `RenderSessionState` | `ACTIVE/INACTIVE` 仅由 `RenderSession` 自身读写 | 同一对象内用 `boolean active` 表示；激活/停用的 `generation` 递增规则不变 |
| `MazeAlgorithmCatalog` | 唯一调用者是 `MazeController`；又依赖通用 `AlgorithmCatalog` 获取注册表 | 将 `mazeAlgorithms(role, model)` 放入已有 `AlgorithmCatalog`，不再维护第二个 Catalog 类型 |
| `RenderSurfaceHost.register/unregister` 私有方法 | 仅转发一次接口调用，没有校验或状态管理 | 在 `attach/detach` 中直接调用 `lifecycle`，保留原有异步执行顺序 |

**保持不变的语义：** 渲染会话的激活幂等性、停用令牌与旧事务失效机制、
`RenderSurfaceHost` 每个 session 的串行化、迷宫生成器/寻路器按 `MazeRole/MazeModel` 分类的方式。

## 检查后决定保留的抽象

- **`DataReader` / `DataWriter` / `DataCodec`：**
  分别表达输入、输出与双向编解码能力，`FileDataIO` 可以只依赖所需的读或写能力；
  合并会让单向输入/输出也被迫实现不相关的方法。
- **`RenderPort`、`RenderSurfaceLifecyclePort`、`PresentationSurfacePort`：**
  分别隔离提交、FX surface 的异步生命周期、以及非结构面板的注册和刷新。
  `RenderSurfaceHost` 必须保留“注销/停用/释放”的顺序与故障传播，
  不能仅因为它只有一个默认实现就删除边界。
- **`StructureMetricsRegistry` / `StructureMetricsProvider`：**
  现有多个独立的数据结构指标计算器；按运行时状态类型与结构 ID 查找确有多态需求，
  不应合并成一个不断增长的条件分支。
- **`ExecutionGate`、`RunControl` 与执行运行时：**
  运行控制涉及暂停、取消、单步与线程协作，
  简化前必须有针对竞态、取消和事件顺序的测试，不能机械内联。
- **`ValueAdapter` 与 `ValueProjection`：**
  前者负责文本输入解析，后者负责展示，是不同职责。
  复杂值展示应使用 `@ValueField`，而不是再创建并行的 Presenter。

## 暂不动的复杂区域

- 渲染邮箱 `RenderMailbox` 的不同最新优先队列、动画顺序与失效规则：
  虽然代码较多，但每种事件有不同调度语义。贸然把队列合并会改变交互与动画。
- `SnapshotWorkspace` 和回放执行历史：含快照选择、恢复与算法输入身份校验，
  建议先写运行时行为回归，之后再评估是否合并同一层级的状态容器。
- Telemetry 的会话和内存诊断：包含 JFR/JOL 与探针生命周期，
  它们不是单纯的 UI 展示包装，不能只因类型数量多就直接删。

## 后续清理准则

1. 优先删除**重复状态源、纯转发包装、同一个查询的多个注册表**。
2. 只有一种调用方、没有独立约束/实现/测试替换点的内部类型，考虑合并到使用者。
3. 不动已经建立的并发、回放、业务值和外部 I/O 边界，除非有等价测试证明行为保持。
4. 不为了少几个类把多个独立职责塞进一个“万能”管理器。
5. ALG 的 Git 提交说明继续使用中文，改动提交前进行编译和适用的回归。


## 第二轮：执行与快照工作区

| 原设计 | 调用链证据 | 处理 |
|---|---|---|
| `LocalClientExecutionService.LocalExecutionHandle` | 仅把 `ExecutionSession` 的事件、完成结果、暂停、恢复、单步和关闭方法逐项转发，没有新增状态或校验 | 让 `ExecutionSession` 直接实现既有 `ExecutionHandle`；服务原样返回运行会话。保留 `ClientExecutionService` 的控制器边界 |
| `SnapshotWorkspace.createInspectorCurrentSnapshotCard/createInspectorSnapshotCard` | 两个方法分别绘制当前/已保存卡片，但布局、选择状态、事件、描述标签完全相同，仅标题和右侧状态文案不同 | 合并为私有 `createInspectorSnapshotCard(..., current, selected)`，保留当前和已保存卡片的原有样式/行为 |

### 检查过但未合并

- `SnapshotWorkspace.selectedSnapshotIds` 是与 `MainController` 共享的**同一个 Map 引用**，不是两份独立状态；外部只使用于管理选中快照，不宜把它误判为状态重复。
- `InMemoryStructureSnapshotStore` 和 `InMemoryRunHistoryService` 保存不同内容、不同的最大条数限制，前者可以恢复算法输入，后者用于同一次运行的比较与导出，不能简单统一成“通用历史库”。
- `PlaybackController`、`ReducedEventTimeline` 与 `ControllerExecutionArchive` 分别管理播放进度、事件索引与有效执行记录；合并会混入并发时序与持久数据的职责。
- `ClientExecutionService`、`ExecutionHandle` 是控制器和具体运行时之间真正使用的契约，可以保留；无须在契约之外创建只做一对一转发的 `LocalExecutionHandle`。
- `InputFingerprint`、`ExecutionExporter` 可作为测试替身及文件 I/O 边界；目前没有发现导致错误状态或性能浪费的平行实现，暂不删除。

下一轮如果打算减少 `MainController`/运行时的成员状态，先补覆盖重播中途切换模块、
历史恢复、快照丢失和保存输入切换的端到端测试，再评估是否需要更深层的数据流重构。


## 第三轮：Runtime、Telemetry、Metrics 和组件发现

### 已落实：指标去重和注册校验收敛

| 位置 | 审查发现 | 处理 |
|---|---|---|
| `LinkedMetricsProvider` / `TreeMetricsProvider` | 对插入、删除分别使用 `nodeInsertions`/`nodeRemovals` 键，而通用 `DefaultAlgorithmMetricsProvider` 使用 `insertions`/`removals`；两个计数显示同一个中文指标名称，容易重复 | 统一使用 `MetricKeys.INSERTIONS` 和 `MetricKeys.REMOVALS`；有权威事件贡献时以其为准，缺失时保留结构事件计数作为补充 |
| `RuntimeOverviewService.build` | 每加入一条结构指标，都重新遍历已加入的算法指标寻找相同键 | 使用现有 `Set<String>` 一次维护已出现的键；保持通用指标在前、结构补充在后的顺序 |
| `AlgorithmDiscovery` / `StructureDiscovery` | 单条 Descriptor 校验完成后，批量唯一性验证又调用相同校验，然后 `ComponentRegistry` 构造时再执行一次 | Discovery 由末尾的 `validateUnique*()` 完成单条校验与批量去重；Registry 仍验证任意外部传入的描述符 |
| CI | 指标拓扑检查原先只编译未执行，注册发现也缺少验证 | 新增 `MetricsDeduplicationChecks` 与 `RegistryDiscoveryChecks`，并执行原有 `PerformanceRegressionChecks` |

### 核对后不应机械合并的部分

- **Runtime 统计与 Telemetry 不是同一份数据的双重采集。** `StatisticsReducer` 从领域事件得到算法逻辑指标（比较、插入、访问等）；`RuntimeMetricTracker` 从可视化状态取得峰值（节点数、高度等）；`ResourceSampler` 是执行期间的轻量主机资源测量；`MemoryTelemetryService` 专门管理周期性探针、JFR/JOL 诊断、快照和分析记录。采样粒度及用途不同，贸然合并会损失性能隔离和历史语义。
- **`IndexedExecutionEvents` 虽然保存额外的事件列表和类型直方图，但用于避免概览每次刷新都扫描全量算法事件。** 它与权威 `ExecutionSession` 事件存储不同：前者是 UI 增量索引，不能作为执行真相或导出来源。
- **`ComponentDiscovery` 的延迟单例注册表值得保留。** 结构和算法扫描已通过静态 Holder 共享；分别从 `StructureDiscovery`、`AlgorithmDiscovery` 返回描述符，是为了让模块能独立发现和验证，不能简单把扫描合成一个巨型类型。
- **`MainController.refreshStructureSummary()` 会读取 `structureOverview()` 与 `structureSummaryText()`，表面存在重复计算，但 `TreeController` 覆写了 `structureSummaryText()` 来展示树根和树高。** 没有复核专属摘要需求前不能把两者直接替换成同一份通用文案。
- **`TreeMetricsProvider` 和 `GraphMetricsProvider` 的拓扑派生缓存**以不可变视图内集合的对象身份失效，避免动画高频帧反复求树高、连通分量；并非可以简单删除的重复状态。

后续如果还要降低 Runtime/Telemetry 开销，应先做采样频率及内存占用基准，
并加入运行中暂停/取消、模块切换、多个并发诊断会话的回归，然后再考虑共用调度或缓存。


## 第四轮：控制器刷新与 CI 收敛

- **CI 只做编译。** `.github/workflows/build.yml` 仅对 `dev` 的 push/PR 使用 JDK 21 执行全模块 `mvn compile`；
  移除对 `start.py`、Python 依赖、测试编译、回归测试执行、`install` 的 CI 依赖。
  测试源码保留，开发者仍可在本地按需执行。
- **`MainController.refreshTopContext()` 是纯空操作。** 曾作为
  `WorkbenchPlaybackShell` 的回调，以及十多处手动调用存在；
  删除空方法和调用，回放按钮不再接收无效的 `refreshContext` 回调。
  `FamilyNavigator` 和现有工作区状态仍是对应 UI 的实际数据来源。
- **消除控制器的一对一转发。** 由 `MainController` 直接调用
  `WorkbenchEventText`、`WorkbenchTelemetryPresentation`、
  `WorkbenchPlaybackShell` 的对应方法，删除多余的私有代理方法及未使用的事件标签代理。
- **回放工具栏读取一次控制器即可。** `WorkbenchPlaybackShell` 的按钮操作和状态刷新
  在一次回调中复用同一个 `BaseController` 引用，不再多次调用相同的 `Supplier.get()`。
- **结构事件计数不用复制历史。** `BaseController` 的两处
  `structureTimeline.events().size()` 改为 `structureTimeline.size()`，
  保持事件起点索引的原始语义，同时避免每次结构操作前复制全量事件列表。

本轮**不合并** `BaseController` 的 `lastExecution`、`lastTimeline`、
`lastExecutionAnchors`：它们分别承担有效执行记录、可回放不完整运行和锚点展示，
并不总能从同一个记录中取得。也保留 `structureEventSnapshot` 的按大小缓存，
因为 `Timeline.events()` 必须生成防御性列表副本，而多个面板会频繁读取结构事件。
`TreeController.structureSummaryText()` 提供专属树摘要，不能直接替换为通用 Metrics 文本。


## 第五轮：执行事件所有权与回放帧索引

审查 `ExecutionSession`、`BoundedExecutionEventStore`、`ReducedEventTimeline`、
`PlaybackController`、`IndexedExecutionEvents`、`BaseController` 的生产、消费和随机跳转路径。

### 已落实

- **消除双份播放帧索引。** `ReducedEventTimeline` 已维护 `currentIndex` 和
  `currentEventIndex` 并负责 `seek/restart`；`PlaybackController` 原先额外维护
  `currentIndex`，每次 `load/seek/step/restart` 都必须两处同步。现在控制器
  的 `currentIndex()/nextIndex()` 和步进判断直接读取时间轴，不再有两套真相；
  播放锁、计时和 generation 失效保护仍保留。
- **删除不产生行为的代理方法。** `ExecutionSession.retire()` 只执行
  `close()`，使用者 `LocalAlgorithmExecution` 已直接关闭会话；回放的
  `consumeState()` 只转发到 `stateConsumer.accept()`，已就地调用。
- **一次事件定位只读取一份历史视图。** `BaseController.seekEventIndex()`
  在一次调用中保留相同的 `ReducedEventTimeline` 和它的不可变 `events()`
  列表引用，后续边界判定、索引计算、事件读取共用该引用。

### 有意保留的不同数据形态

- `BoundedExecutionEventStore` 是**唯一的执行事件权威仓库**，承担容量上限与终止事件保留；
  对外导出和创建执行记录读取其防御性快照，不能交给 UI 缓存替代。
- `ReducedEventTimeline` 持有可视帧索引、稀疏 checkpoint 和最终可视状态，
  是为了 O(log n) 定位历史帧及减少重放；不可与实时指标计数器合并。
- `IndexedExecutionEvents` 除了保存递增事件列表，还维护事件类型直方图；
  `MetricsSupport.countEvents()` 能用该索引避免每次指标刷新全量重扫。
  此外它作为 `List<EventEnvelope>` 传给现有指标提供器；在未明确收敛整个
  指标接口前，不为了省掉这份 UI 缓存破坏现有契约。
- `ExecutionSession` 的 `runtimeCompletion` 与 `presentationCompletion`
  分别代表执行和界面回放消费完成，失败与结束时刻不同，不能合并成单个 Future。
- 结构日志事件来自 `Timeline`，和算法执行回放事件流来源不同，应分开。
  `BaseController.structureEventSnapshot` 的按长度缓存避免每次 JavaFX 概览刷新重复复制历史。

本轮 CI 按开发用途**仅编译主源码**，不自动运行回归或打包部署；
本节记录的是代码路径的静态审查与编译验证，不将其表述为完整的交互验证。


## 第六轮：事件时间轴只更新游标，不重建整个标记视图

原先 `MainController.refreshExecutionPresentation()` 每次状态变化都调用
`TimelineMarkerPanel.rebuild()`；后者每次都重新获取事件历史、线性筛选、
分桶，并删除和重建全部 JavaFX `VBox/Region/Tooltip`。一次回放进度变化
不应触发全量历史计算。

- `BaseController.executionEventRevision()` 提供只读轻量版本：
  启动新历史、收到实时事件批次、切换执行完成后的权威时间轴、
  清空执行状态时递增。时间轴 UI 无需先复制 `executionEvents()` 才能判断是否变化。
- `TimelineMarkerPanel.refresh()` 比较当前控制器、事件版本、
  控件尺寸与字号。如果都未变化，只调整**现有**光标位置、聚合标记
  的选中样式；事件源、类别筛选、控件几何、字号或语言改变时才调用
  `rebuild()`。语言变化由原有 locale listener 显式触发重建 Tooltip。
- 分组的代表事件不再由当前游标决定。隐藏的事件类别不会由于选中而
  突然显示分类标记，但独立的游标依然标示该事件在时间轴中的准确位置。
- 聚合组本来按事件索引升序存储；刷新选中状态及点击聚合标记跳往
  下一事件改用二分查找，避免大型聚合组每次回放都线性搜索。
- `TimelineMarkerPanel` 仅缓存最多数十个已渲染标记引用、分组索引以及
  版本、尺寸等失效信息，不创建第二套权威事件存储。

重要边界：实时算法运行时，事件历史仍会增长，版本变化时会重建分组；
这里只消除了**历史未变时**的冗余分组与控件重建，不声称消除所有大型
实时事件流的刷新开销。CI 只执行主源码编译，未进行 JavaFX 交互测试。

收尾修正：主动停止一个仍在运行的会话时同样递增事件版本，使标记缓存失效；
移除 `TimelineMarkerPanel` 构造函数中只传递 `WorkbenchEventText.eventDisplayName`
静态方法的一次性 `Function` 参数，改由同包面板直接调用，少一层无用的注入。


## 第七轮：实时事件增长时避免反复复制与重新分类

继第六轮把时间轴游标刷新与节点重建分离后，进一步审查实时阶段的事件增长：

- 原 `TimelineMarkerPanel.rebuild()` 每次调用 `BaseController.executionEvents()`；
  运行期间此方法通过 `ExecutionSession.events()` 取得**完整权威快照**。
  正常实时刷新并不需要再次复制所有已到达的事件。
- 现在 `BaseController.timelineMarkerEvents()` 在时间轴 UI 内返回
  `IndexedExecutionEvents` 的**不可修改借用视图**（并不构造第二份历史）；
  当异步索引完成且 `lastTimeline` 可用时，自动切换至其不可变权威事件列表。
  借用视图只允许在 JavaFX 线程中即时读取，不用于外部持久存储、
  导出、跨线程遍历或异步处理。`executionEvents()` 的普通防御性快照契约不变。
- `TimelineMarkerPanel` 只增量维护**可显示类别对应的整数事件索引**。
  同一事件源追加新事件时仅对新增区间进行分类判断；
  当输入重置、来源切换、类别开关变化、控件重建时丢弃缓存并重新索引。
  原有分桶、聚合标记的导航与 Tooltip 仍对当前全部候选索引计算，
  不改变布局结果与每组可跳转的事件集合。
- 将渲染事件数量直接使用已扫描数量，避免额外维护同义状态字段。

本轮**没有引入额外事件存储、定时任务、节流策略或新的架构接口**。
虽然消除了每个实时批次的 O(N) 事件副本与历史分类重扫，分桶和
JavaFX 标记仍需随着事件总数变化而更新：保持全局时间比例的准确性，
不能假装它们可以零成本地增量追加。

CI 按项目要求仍只检查主源码编译，不运行回归测试、不打包、不部署。


## 第八轮：结构指标上下文不再按刷新次数重扫历史

检查发现 `BaseController.structureEvents()` 已缓存按操作增长的不可变历史；
真正重复的工作在 `StructureMetricsContext`：

- 旧版 `eventCount()`、`operationCount()` 和每种 `count(EventType.class)`
  都会重新扫描整个 `events`。数组、树、字符串、链表等提供器在
  **同一次**概览构造中也会执行多次完整扫描。
- 保留原有 `StructureMetricsContext` 类型，内部改为构造时一次遍历，
  汇总结构事件总数、涉及的运行 ID 数量和具体事件类型的计数。
  `count()` 只遍历少量已出现的事件类型，仍支持子类及父类的
  `isInstance` 等价匹配，未将非结构事件计入总数。
- `BaseController` 在 `structureEvents()` 缓存新历史快照时丢弃
  旧统计上下文；结构日志作用域 ID 改变时也重新建立。
  时间轴游标移动、算法帧刷新但结构历史没变时共用同一份不可变汇总。
- `StructureMetricsRegistry` 和 `RuntimeOverviewService` 增加接收
  现有汇总对象的调用入口，原本接收事件列表的入口保留；
  调用者无需新增适配器或迁移。
- `RuntimeMetricTracker`、实时算法事件索引、资源采样和各类拓扑缓存
  均不变，统计口径仍由各具体 MetricsProvider 定义。

没有新增框架实体或“通用缓存管理器”。此项优化将结构事件的历史汇总
从每次概览的多次全量扫描缩减为**每次结构历史变化只扫描一次**。
项目 CI 依照约定只编译主源码，运行时统计/JavaFX 交互仍需开发机实际验证。


## 第九轮：结构操作日志只投影新增事件，避免复制全量历史

沿着 `BaseController.executeStructureOperation()`、`recordAuxiliaryEvent()`
→ `Timeline` → `ControllerLogChannels` → `LogChannel` 的实际调用链检查：

- 原来每次操作结束后用 `structureEvents()` 取得**全部累计事件**快照，
  `appendStructureEventsSince(allEvents, start)` 却只读取操作开始索引之后的部分。
  即使一次操作只产生少数事件，也会因为累计历史增长而每次复制全部数据。
- `Timeline.eventsSince(startIndex)` 在原有同步边界内，仅返回对应区间的
  不可变快照；起点仍按旧调用的行为截断到合法区间。
  两个调用方直接传入本次新增事件，避免为日志无意义地刷新全部结构历史快照。
  `structureEvents()` 仍保留自己的按大小缓存，供结构详情和指标系统使用。
- `ControllerLogChannels` 按原顺序过滤执行生命周期事件、
  保留业务 `LogEvent` 的等级与标签，并为其他结构事件保留
  原来的操作名裁剪和 `INFO` 级别。
  区别是现在先投影成既有的 `LogEntry`，只向 JavaFX 提交**一次批次更新**，
  不再对每条事件分别发送刷新任务。
- `LogChannel.appendAll()` 利用原有 `ObservableList.addAll()`
  一次写入本次日志记录，避免为每条日志独立触发集合更新；
  没有引入新类型、异步队列或另一个日志缓存。

按累计历史事件数为 N、单次新增事件数为 k 计算，
日志快照从每次 O(N) 缩减为 O(k)；统计系统独立的不可变快照仍按需要生成。
日志通道和结构操作的业务语义不变。项目 CI 仅验证主源码编译，
不声称覆盖了 JavaFX 实际交互或运行时性能基准。


## 第十轮：限制工作台日志内存与减少重复 UI 发布

进一步复核了 `LogChannelStore`、`LogChannel`、
`MainController.refreshExecutionPresentation()`、`WorkbenchPlaybackShell`：

- `LogChannelStore` 以 `LogChannelId` 路由独立日志通道，不存在第二套日志仓库；
  通道身份包括结构、算法和系统，合并所有日志通道会破坏独立检索/切换，故**保留**。
- `LogChannel` 的 JavaFX `ObservableList` 此前没有保留上限。长时间运行
  会积累大量 UI 日志行。现在**每个通道最多保留约 10,000 行**，达到阈值后
  批量裁剪至最近 8,000 行，避免每追加一条都搬移整个列表。
  特别大的单次日志批次直接取末尾 8,000 行，避免先插入大量无效 UI 条目。
  这是明确的**日志保留语义变化**：超过容量的旧界面日志不再可见。
  权威结构/算法事件历史不受此上限约束，不把 UI 日志当作完整执行记录。
- `MainController.refreshExecutionPresentation()` 原先对非算法事件先调用
  `refreshRunSummary()`，再调用 `refreshStructureSummary()`，
  两条路径都可能发布相同的内存面板，造成一次事件刷新内两次发布与失效通知。
  现在结构/生命周期事件优先刷新结构摘要与内存，只额外发布必要的统计模型；
  普通算法事件仍由 `refreshRunSummary()` 处理，不改变对应面板的更新条件。
- `WorkbenchPlaybackShell.refreshTimelineStatus()` 原先每次刷新都删除、添加
  状态点 CSS 类，即使 `RUNNING/PAUSED/COMPLETED` 状态未变。
  现在先检查是否已经具备目标样式，仅状态变化时才调整 CSS 类。
- `VisualizationSurface.setObstructionInsets()` 本来已经对相同 `Insets`
  做相等性检查，不会重复触发 viewport 通知，因此不需要再引入第二层
  控制器侧缓存。

以上改动没有新增框架抽象或部署流程。CI 保持 JDK 21
`mvn -B -ntp -DskipTests compile`，仅主源码编译，不执行 UI 交互测试。
