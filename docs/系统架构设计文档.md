# Algorithms V2 系统架构

## 1. 总体边界

```text
                         META-INF/algorithms.factories
                                  │
                                  ▼
                           ModuleLoader
                                  │
                                  ▼
                           ModuleRegistry
                                  │
                ┌─────────────────┴─────────────────┐
                ▼                                   ▼
          Data Structure                         Algorithm
                │                                   │
                └──────────────┬────────────────────┘
                               ▼
                       ExecutionRuntime
                               │
                         EventEnvelope
                               │
          ┌───────────┬────────┼────────┬─────────────┐
          ▼           ▼        ▼        ▼             ▼
       Timeline    Statistics Logging  Client       Server
                                      Playback     recording
```

核心职责：

- Registry：决定请求由哪个实现负责。
- Runtime：决定一次执行如何启动、暂停、单步、恢复、取消和结束。
- ExecutionEvent：描述领域中发生了什么。

## 2. core

`core` 是纯 Java 可复用层，包含：

- event / EventEnvelope / EventSink
- ExecutionRuntime / RunControl
- ExecutionScheduler
- ModuleLoader / ModuleRegistry
- Timeline
- Snapshot 数据契约
- Statistics / ExecutionSummary / ExecutionTiming
- Logging

禁止依赖 JavaFX、FXML、Spring HTTP、数据库 UI 或具体动画概念。

### 2.1 ExecutionEvent 与 EventEnvelope

领域代码只创建 ExecutionEvent。Runtime 自动包装：

```text
runId
operationId
sequence
timestamp
source
event
```

领域代码不手工维护这些运行元数据。

### 2.2 Runtime 控制

RunControl 提供：

- pause
- resume
- live step
- cancel

Live step 的语义是：暂停后放行下一个领域事件。生命周期事件与执行门顺序由 Runtime 保证，例如 Resume 必须先进入事件流，再允许 worker 继续完成。

### 2.3 Scheduler

算法/结构实现不创建执行线程。Client worker 与 Server 执行池都通过 core `ExecutionScheduler` 创建。

Client 的 JavaFX animation scheduler 属于 presentation 边界，因此保留在 client。

### 2.4 Statistics 与 Timing

core Statistics 只统计 headless 可理解的信息：

- totalEventCount
- domainEventCount
- lifecycleEventCount
- domain metrics
- event span
- Runtime total duration
- resource usage（如果宿主提供）

visual frame 与 playback duration 不属于 core。

## 3. algorithms

`algorithms` 包含真实结构和算法实现。

### 3.1 一等结构

当前注册：

```text
structure.array.Integer
structure.linked-list.Integer
structure.stack.Integer
structure.queue.Integer
structure.tree.Integer
structure.graph.Integer
structure.hash-table.String.Integer
structure.string.String
```

结构契约保持领域语义：

- Array：get/set/insert/remove/swap/raw
- LinkedList：insert/remove/update/raw
- Stack：push/pop/peek
- Queue：enqueue/dequeue/front/rear
- Tree：insert/remove/find/raw；RotatableTree 明确 rotateLeft/rotateRight
- Graph：vertex/edge/neighbors/raw
- HashTable：put/get/remove/bucket state
- String：replace/insert/remove/update/raw

### 3.2 算法接口

不存在万能 `Algorithm.run(Context)`。

重要领域行为必须由实现显式实现。例如 Sort 必须实现 compare 和 sort。

Maze 生成器/寻路器仅共享领域接口，BFS、DFS、Union-Find、A* 的核心流程分别存在于具体类中，不通过 Strategy 枚举分支。

### 3.3 事件原则

读取操作通常不产生事件。结构修改和算法关键语义产生必要事件。

结构事件由结构产生；算法事件由算法产生。例如排序 swap 由 MutableArray 产生 Swapped，QuickSort 只额外产生 Pivot/Range/Compare 等算法语义。

## 4. client

Client 只负责 presentation：

- Workbench shell
- JavaFX controls
- visualizer
- reducer / ViewState
- live playback queue
- replay
- client execution history/export
- snapshot cards

### 4.1 单工作区双模式

Client 只有一个 Workbench shell；Structure 和 Algorithm 是同一个工作区的两个互斥模式，不做桌面双栏。任何屏幕尺寸都只显示当前模式。

Structure 模式拥有唯一可编辑结构；Algorithm 模式不维护第二份可编辑结构，而是复用当前结构快照或已保存 Snapshot，并从 Snapshot 创建隔离的算法运行副本。算法完成、取消、回放都不反写 Structure 状态。

Structure-only 模块（LinkedList/Stack/Queue/HashTable）不会伪造算法入口。

交互约束：

- Structure 模式不显示算法执行 Dock，避免在结构编辑页面误启动算法。
- Algorithm 模式标题区必须显示当前输入来源：当前结构快照、已保存 Snapshot，或无结构输入的算法参数。
- 算法运行期间锁定 Structure/Algorithm 模式切换与模块导航，避免共享 visualizer 被跨模式事件覆盖。
- 选中已保存 Snapshot 作为算法输入后，后续编辑当前 Structure 不会使该 Snapshot 对应的算法结果/回放失效。
- 窄窗口仍保留 Snapshot 面板，只压缩宽度，不隐藏这一核心能力。
- Maze 生成算法的结果先属于 Algorithm 状态，不自动写回 Structure；只有显式“应用结果到结构”才提交为当前 Maze Structure。Maze 生成器使用算法参数，寻路器使用当前/已保存 Maze Snapshot。

### 4.2 Snapshot

Snapshot state 使用 core 数据契约，不存 ViewState。

对 Array/Tree/Graph/String：Algorithm 模式选择当前结构快照或已保存 Snapshot 作为输入。运行算法时从 Snapshot 构造独立副本，不反写 Structure。切换回 Structure 后仍继续编辑唯一的 live structure。

Tree Snapshot 保存稳定 nodeId、height 和 topology；作为算法输入时精确恢复这些信息，而不是只拿 value 重新插入。

### 4.3 Reducer / Timeline

Reducer、Reduction、visualFrame、EventImportance 属于 client，因为它们决定如何把权威事件投影成 UI 状态和可见帧。

权威 EventEnvelope 流不会因为某个事件不生成可视帧而丢失。

### 4.4 Runtime 与播放解耦

算法 worker 产生权威事件后立即继续，不等待动画 delay。

JavaFxEventSink 是独立有序播放队列。播放速度、播放暂停/单步不会改变 Runtime total duration。

## 5. server

Server 依赖 core + algorithms，无 client 依赖。

`AlgorithmsController` 负责 HTTP 边界；`AlgorithmExecutionService` 负责目录和异步执行。Registry 选择真实实现，Runtime 管理一次执行，RecordingEventSink 保存权威事件和统计。

DTO 只在 HTTP 边界存在。例如 GraphBfsRequest 会先转换成 MutableGraph，再调用 GraphBfs.traverse。

## 6. 扩展一个实现

结构：

1. 明确领域契约和 raw 表示。
2. 实现真实数据结构。
3. 只对必要修改产生结构事件。
4. 在资源 KV 中增加明确的 structure key。
5. Client 如需要再增加 structure controls / visualizer / Snapshot support。

算法：

1. 定义真实领域方法，不创建通用 Runner。
2. 直接实现算法核心流程。
3. 使用 ExecutionEvents 发布必要领域事件。
4. 在资源 KV 中增加 algorithm key。
5. Client reducer 与 Server DTO 都作为边界消费者，不反向进入算法层。

## 7. 禁止回退到的模式

- AlgorithmProvider / ProviderCatalog
- DefaultAlgorithmRunner
- AlgorithmContext / giant OperationContext
- IntegerSortSupport / TreeSupport / GraphSupport
- Strategy 枚举隐藏多个真实算法
- 算法 Thread.sleep 控制动画
- core 存 visualFrame / JavaFX playback 语义
- client/server 各自重新实现 Runtime 生命周期
