# 系统架构设计文档

## 1. 文档定位

本文描述当前项目的模块边界、算法执行链和可视化数据流。它是架构基线，不等同于服务端接口实现清单。

服务端的阶段目标、HTTP 路径、限流和在线代码执行规划，单独维护在[服务器长期实现维护文档](服务器长期实现维护文档.md)中。

当前架构的核心目标是：算法只依赖通用执行协议，JavaFX 客户端和未来的网页服务端分别消费同一套算法能力，但彼此不形成依赖。

## 2. 模块总览

```text
                    ┌────────────────────┐
                    │        client      │
                    │ JavaFX/FXML/CSS/UI │
                    └─────────┬──────────┘
                              │ 依赖
                    ┌─────────▼──────────┐
                    │     algorithms     │
                    │ ProviderCatalog    │
                    │ 算法、输入、输出、事件 │
                    │ basic 数据结构      │
                    └─────────┬──────────┘
                              │ 依赖
                    ┌─────────▼──────────┐
                    │        core        │
                    │ API、执行运行时、事件 │
                    │ 生命周期、归约、统计 │
                    └────────────────────┘

                    ┌────────────────────┐
                    │       server       │
                    │ 当前为 Spring Boot │
                    │ 启动骨架            │
                    └─────────┬──────────┘
                              │ 当前仅依赖
                              ▼
                             core

                    ┌────────────────────┐
                    │        other       │
                    │ 练习代码和独立实验   │
                    └─────────┬──────────┘
                              ▼
                         algorithms
```

依赖规则如下：

- `core` 不依赖 `client`、`server`、JavaFX、Spring Boot 或客户端渲染器。
- `algorithms` 依赖 `core`，提供正式算法和算法目录；它不依赖 JavaFX。
- `client` 依赖 `algorithms` 和 `core`，负责桌面交互、动画、回放和渲染。
- `server` 不依赖 `client`。当前只依赖 `core`；服务端开始执行内置算法时，再按需要依赖 `algorithms`。
- `other` 是练习和实验模块，不属于客户端或服务端的生产执行链。

## 3. 各模块职责

### 3.1 core：公共协议和执行内核

`core` 是最内层模块，主要包含四类内容：

1. **算法扩展 API**：`Algorithm<I, O>`、`AlgorithmInput`、`AlgorithmOutput`、`AlgorithmProvider`、`AlgorithmInvoker` 和 `AlgorithmContext`。
2. **执行运行时**：`DefaultAlgorithmRunner`、`RunControl`、取消令牌、执行门、事件接收器和执行结果。
3. **事件协议**：`ExecutionEvent` 负责给算法事件补充 `runId`、`algorithmId`、序号和时间；算法本身只产生事件负载。
4. **通用归约和统计**：`EventReducer<S>`、`ReductionCursor`、`ExecutionRecording`、`ExecutionStatistics` 和指标归约器。

`core` 不知道“节点应该画成什么颜色”“迷宫应该使用 Canvas 还是 SVG”，也不保存 JavaFX 视图状态。它只提供可以被不同运行环境实现和消费的协议。

### 3.2 algorithms：正式算法库和数据结构

`algorithms` 负责实现具体算法，并提供唯一的生产注册入口 `ProviderCatalog`。当前算法按领域组织：

- `sort`：整数排序及比较、写入、交换、区间、枢轴和完成事件。
- `tree`：AVL 操作、稳定节点快照、旋转和结构变更事件。
- `maze`：数组迷宫、图迷宫生成，以及数组迷宫寻路。
- `graph`：整数图、边模型和 BFS 事件。
- `basic`：可复用的基础容器、节点、并查集和历史练习所需的基础结构。

每个可发布算法都应提供：

```text
Input        明确、可校验的输入模型
Output       明确的结果模型
Event        可排序、可回放的领域事件
Algorithm    只依赖 AlgorithmContext 的执行实现
Provider     元数据、类型、校验器和工厂
```

`ProviderCatalog` 负责 ID 到 Provider 的显式映射。执行端可以通过 ID 查询算法，但不能通过客户端提交的类名或反射路径加载任意类。

### 3.3 client：JavaFX 展示和本地执行适配

`client` 负责所有桌面相关内容：

- JavaFX 控制器、FXML、CSS、国际化文本和窗口生命周期。
- `LocalAlgorithmExecution`：为每次运行创建独立会话、线程、控制器和有界事件存储。
- `JavaFxEventSink`：将权威事件安全地投递给 JavaFX 观察者，不让 JavaFX 线程成为算法协议的一部分。
- 四类 `EventReducer` 和 ViewState：排序、树、迷宫、图分别把领域事件归约成不可变视图状态。
- `PlaybackController` 和 `ReducedEventTimeline`：提供播放、暂停、速度调整、定位、前后单步和终态重建。
- Canvas、GraphStream JavaFX 和其他 renderer：只读取 ViewState，不直接修改算法对象。

本地实时链路不需要 JSON。JSON 只用于文件导出，或者未来服务端定义网络 DTO 后的 HTTP/SSE 边界。

### 3.4 server：未来的服务端适配层

当前 `server` 只有 Spring Boot 启动类，尚未实现算法目录、执行会话或 SSE。未来服务端应负责：

- 将 HTTP 请求转换为白名单输入模型。
- 创建独立执行会话并调度有界后台任务。
- 保存权威事件、结果和执行统计。
- 通过 SSE 或其他网络协议向网页客户端提供事件。
- 执行并发数、输入规模、事件数、输出大小和超时限制。

服务端可以复用 `core` 的执行协议，也可以在需要执行内置算法时依赖 `algorithms`；但不应依赖 `client` 的 reducer、JavaFX 控制器、CSS、GraphStream JavaFX 视图或 `AlgorithmLabels`。

## 4. 算法类型边界

算法在静态代码中保持强类型：

```java
public interface Algorithm<I extends AlgorithmInput, O extends AlgorithmOutput> {

    O run(I input, AlgorithmContext context) throws InterruptedException;
}
```

动态选择算法时，边界由 `AlgorithmProvider` 和 `AlgorithmInvoker` 负责：

```text
algorithmId
    ↓
ProviderCatalog.find/require
    ↓
AlgorithmProvider
    ↓ prepare(input)
TypedAlgorithmInvoker
    ↓
新建 Algorithm<I, O> 并执行
```

这样既保留了算法内部的输入/输出类型检查，又允许控制器、服务端目录和未来网页请求通过统一 ID 选择算法。泛型擦除只发生在注册表和调用边界，不应扩散到算法实现内部。

## 5. 一次执行的完整时序

```text
控制器或服务端
    │ 选择 algorithmId 和输入
    ▼
ProviderCatalog
    │ 找到 Provider，校验并准备输入
    ▼
AlgorithmInvoker
    │ 创建全新的算法实例
    ▼
DefaultAlgorithmRunner
    │ 创建 runId、Context、RunControl 和事件序号
    ▼
Algorithm.run(input, context)
    │
    ├─ context.checkpoint() 检查暂停/取消
    └─ context.emit(payload) 发布领域事件
              ▼
       ExecutionEvent（运行时封装）
              ▼
       权威 EventSink / EventRecording
              ├──────────────► ExecutionStatistics
              └──────────────► EventReducer<S>
                                      ▼
                                不可变 ViewState
                                      ▼
                         实时 renderer 或回放时间轴
```

运行结束后，运行时发布成功、取消或失败的生命周期事件。结果和统计与事件记录属于同一个执行会话，不能把不同 `runId` 的事件混在一起。

## 6. 事件与 EventReducer

### 6.1 事件分层

算法只负责产生领域事件负载，例如 `SortSwappedEvent`、`AvlTreeEvent.StructureChanged`、`ArrayMazePathEvent.Backtracked` 或 `GraphBfsEvent.EdgeExamined`。

运行时负责生成统一信封：

```text
ExecutionEvent {
    runId
    algorithmId
    sequence
    occurredAt
    payload
}
```

因此算法不能伪造运行 ID 或序号，观察者也可以验证事件是否连续、是否来自同一次执行。

### 6.2 归约模型

`EventReducer<S>` 是无状态转换器：它只读取“上一个状态”和“当前事件”，返回新的状态、事件重要性和是否生成可视帧。

```text
旧状态 S + ExecutionEvent
              │
              ▼
Reduction<S>
    ├─ state
    ├─ stateChanged
    ├─ importance
    └─ visualFrame
```

`ReductionCursor` 保存一次回放所需的当前位置，并校验 `runId`、`algorithmId` 和连续序号。相同的事件序列可以被实时消费、完整回放、时间轴定位或单步执行。

### 6.3 四类视图状态

- **排序**：保存当前数组、比较位置、写入位置、交换位置、区间、枢轴和已完成元素；旗帜上的数字直接来自当前数组值。
- **树**：保存稳定节点 ID、父子关系、焦点节点、旋转阶段和不可变 AVL 快照；结构变化事件必须能在对应帧体现拓扑变化。
- **迷宫**：分别记录发现、进入、死路、回溯和最终路径，按优先级渲染颜色；寻路过程必须由逐格事件驱动，而不是只在完成事件中发送完整路径。
- **图**：保存节点访问状态、父节点、受检边和遍历顺序；GraphStream 只在 client 的适配器中出现。

## 7. 生命周期、暂停和取消

每一次运行都必须拥有独立的运行控制对象，不能使用全局单线程执行器或全局暂停锁。算法在循环和关键步骤调用 `checkpoint()`，由运行时完成：

- 检查取消标记并及时终止。
- 在暂停状态等待执行门恢复。
- 记录运行状态和终态事件。
- 在异常、取消和超时路径上完成资源释放。

JavaFX 的播放暂停与算法执行暂停是两个概念：前者只改变回放游标和播放速度，后者改变算法线程的运行控制。服务端也应保持这两个概念分离。

## 8. 服务端接入边界

服务端未来可以采用如下链路：

```text
HTTP Controller
    ↓ 认证、DTO、输入白名单
ExecutionService
    ↓ ProviderCatalog + AlgorithmInvoker
独立 ExecutionSession
    ↓ 有界线程池和 RunControl
权威事件存储
    ↓
SSE / 查询接口 / 结果下载
```

网络层不要直接暴露 Java 类全名、GraphStream 对象或 JavaFX ViewState。推荐在 `server` 中维护独立的输入/输出 DTO 和事件编码器；它们可以根据 `core` 事件生成稳定 JSON，但不改变 `core` 的领域模型。

候选路径和阶段验收标准见[服务器长期实现维护文档](服务器长期实现维护文档.md)。在服务端实际实现并验证前，本文不把这些候选接口视为已经存在的能力。

## 9. 新增算法的实施流程

1. 在 `algorithms` 中定义输入、输出和领域事件。
2. 实现 `Algorithm<I, O>`，只通过 `AlgorithmContext` 检查控制并发布事件。
3. 实现 `AlgorithmProvider`，补齐元数据、输入类型、输出类型、工厂和校验器。
4. 将 Provider 加入 `ProviderCatalog`，保证 ID 唯一且语义稳定。
5. 在 client 中实现对应的 `EventReducer<ViewState>` 和 renderer；不要让 renderer 直接依赖算法内部对象。
6. 服务端需要开放该算法时，增加输入/输出 codec、策略和网络 DTO，不把 client 代码加入 server。
7. 补充结果、事件顺序、取消、边界输入和回放行为验证。

## 10. 规模和性能约束

逐帧可视化会同时消耗计算、内存和 UI 调度资源。当前设计必须遵守以下原则：

- 每次执行使用独立实例，禁止跨运行共享可变结构。
- 事件记录、有界观察队列和客户端归档都必须有上限。
- 大结构不应无限制地保存每一帧完整快照；必要时使用增量事件、检查点和按需重放。
- 服务端限制只能由服务器收紧，客户端提交的参数不能扩大上限。
- 慢速观察者不能阻塞算法线程；权威记录与实时展示必须解耦。

服务端的推荐初始限制、持久化策略和慢客户端处理方式，以[服务器长期实现维护文档](服务器长期实现维护文档.md)为准。

## 11. 构建和验证边界

架构变更至少应验证：

```bash
# 全部模块测试与验证
mvn clean verify

# 只验证客户端及依赖
mvn -pl client -am test

# 只验证算法库及核心
mvn -pl algorithms -am test

# 验证服务端当前骨架及依赖
mvn -pl server -am test
```

JavaFX 窗口、GraphStream 布局和 CSS 动画需要有图形桌面环境才能进行人工冒烟检查；无显示环境时只能完成编译和自动测试，不能据此保证最终像素效果。

## 12. 当前不属于本架构的内容

- `server` 的具体 Controller、数据库、消息队列、鉴权和 SSE 实现尚未完成。
- 在线输入任意 Java 代码、动态编译和沙箱运行不属于当前内置算法执行链。
- `other` 中的练习代码不自动成为 Provider，也不应被服务端通过反射暴露。
- JavaFX 样式、颜色、布局和动画实现属于 `client`，不能下沉到 `core`。
