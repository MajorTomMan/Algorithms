# Algorithms 系统架构设计

## 1. 系统目标

Algorithms 将数据结构实现、算法执行、过程事件、桌面可视化和服务端运行组织在同一套领域模型之上。

系统的核心关系如下：

```text
                   META-INF/algorithms.factories
                              │
                              ▼
                         ModuleLoader
                              │
                              ▼
                        ModuleRegistry
                              │
               ┌──────────────┴──────────────┐
               ▼                             ▼
         Data Structure                   Algorithm
               │                             │
               └──────────────┬──────────────┘
                              ▼
                      ExecutionRuntime
                              │
                       EventEnvelope
                              │
          ┌──────────┬────────┼────────┬──────────┐
          ▼          ▼        ▼        ▼          ▼
       Timeline   Statistics Logging  Client    Server
                                   Playback   Recording
```

职责划分：

- `ModuleRegistry`：定位结构和算法实现。
- `ExecutionRuntime`：管理一次执行的生命周期。
- `ExecutionEvent`：描述领域中发生的动作。
- `EventEnvelope`：为领域事件增加运行元数据。
- `Timeline / Statistics / Logging`：消费统一事件流。
- `Client`：负责用户交互、可视化和回放。
- `Server`：提供 headless 算法执行能力。

## 2. 模块边界

### 2.1 core

`core` 是纯 Java 公共运行层，包括：

- Event / EventEnvelope / EventSink
- ExecutionRuntime
- RunControl
- ExecutionScheduler
- ModuleLoader / ModuleRegistry
- Timeline
- Snapshot 数据契约
- Statistics
- Logging

`core` 不包含：

- JavaFX 控件或 ViewState
- FXML / CSS
- Spring Web Controller / HTTP DTO
- 动画颜色、动画时长等 presentation 规则

### 2.2 algorithms

`algorithms` 包含真实数据结构和算法实现。

主要结构：

```text
Array
LinkedList
Stack
Queue
Tree
Graph
HashTable
String
```

算法直接依赖领域结构或明确输入对象，并通过领域方法执行。

### 2.3 client

`client` 是 JavaFX presentation 层，负责：

- Workbench
- 结构操作 UI
- 算法选择和参数配置
- Visualizer
- Reducer
- 动画播放队列
- Snapshot UI
- Timeline 回放
- Log / Statistics 展示
- 响应式布局

### 2.4 server

`server` 是 Spring Boot headless 宿主，负责：

- 算法目录 API
- 执行提交
- 运行状态查询
- HTTP DTO 转换
- 后台 ExecutionScheduler
- Runtime recording

Server 不依赖 Client。

### 2.5 other

`other` 用于练习代码、算法题、示例程序和独立实验。它不是生产 Registry 的组成部分。

## 3. Module Registry

### 3.1 注册资源

注册文件：

```text
algorithms/src/main/resources/META-INF/algorithms.factories
```

Key 描述结构族、类型和算法标识，例如：

```properties
structure.array.Integer=...
structure.graph.Integer=...
structure.string.String=...
structure.hash-table.String.Integer=...

algorithm.array.Integer.quick-sort=...
algorithm.graph.Integer.graph-bfs=...
algorithm.string.String.kmp=...
```

### 3.2 加载过程

```text
resource properties
       ↓
ModuleLoader
       ↓
ModuleRegistry
       ↓
create(key, expectedType)
```

Registry 只负责解析实现和创建实例，不负责算法生命周期。

## 4. 结构模型

结构接口应表达各自领域语义，不要求所有结构提供相同的操作集合。

示例：

```text
Array        get / set / insert / remove / swap
LinkedList   insert / remove / update
Stack        push / pop / peek
Queue        enqueue / dequeue / front / rear
Tree         insert / remove / find / rotate
Graph        vertex / edge / neighbors
HashTable    put / get / remove
String       replace / insert / remove / update
```

结构可以通过 `raw()` 暴露必要的底层结构，以支持算法直接处理真实数据。

普通读取操作通常不产生事件；会影响结构状态或算法语义的重要动作才产生领域事件。

## 5. 算法模型

算法保留具体领域方法：

```java
sort.sort(array);
graphBfs.traverse(graph, startNode);
kmp.search(string, pattern);
mazeGenerator.generate(input);
pathfinder.findPath(input);
avl.execute(input);
```

核心算法实现不依赖 Runtime Context、JavaFX 或服务端 DTO。

结构事件和算法事件各自描述自己的领域事实。例如：

- Array 负责 Updated / Swapped。
- Sort 负责 Compare / Pivot / Range。
- Tree 负责 Insert / Remove / Rotate。
- BFS 负责 Visit / Processed。
- KMP 负责 Compare / Fallback / Match。

## 6. Execution Runtime

### 6.1 ExecutionRuntime

`ExecutionRuntime` 管理：

- runId
- operationId
- sequence
- Runtime state
- start
- pause
- resume
- live step
- cancel
- completion / failure
- EventEnvelope 包装

执行内容通过 `ExecutionOperation` 传入。

Runtime 不实现具体排序、搜索、遍历或数据结构逻辑。

### 6.2 RunControl

RunControl 管理实时执行控制。

暂停状态下执行 Step 时，只允许下一个领域事件通过，然后再次保持暂停。

生命周期事件与执行门具有确定顺序。例如恢复执行时，`RunResumedEvent` 会先写入事件流，再允许 worker 继续运行。

### 6.3 ExecutionScheduler

执行线程由 `ExecutionScheduler` 统一创建和管理。

一个 Run 的 EventEnvelope sequence 始终保持单调有序。不同 Run 可以并发运行。

## 7. Event 模型

### 7.1 ExecutionEvent

事件描述领域动作，不描述 UI 行为。

示例：

```text
Inserted
Removed
Updated
Swapped
RotateLeft
RotateRight
Visit
Compare
Pivot
Match
SnapshotCreated
LogEvent
RunCompleted
```

### 7.2 EventEnvelope

Runtime 将事件包装为：

```text
runId
operationId
sequence
timestamp
source
event
```

消费者不需要算法实现者手工提供这些字段。

### 7.3 EventSink

统一事件流可以送往多个消费者：

```text
ExecutionRuntime
   └── EventSink
       ├── Timeline
       ├── RecordingEventSink
       ├── Statistics
       ├── Logging
       └── Client playback
```

## 8. Snapshot

Snapshot 表示结构在某个时点的完整状态。

Snapshot 数据定义在 core，与 JavaFX ViewState 分离。

主要数据类型：

- `SequenceSnapshot<T>`
- `BinaryTreeSnapshot<T>`
- `GraphSnapshot<T>`
- `HashTableSnapshot<K,V>`
- `StringSnapshot`
- `MazeSnapshot`

Tree Snapshot 保存稳定 nodeId 和拓扑信息，可以准确重建结构。

Snapshot 有两种主要用途：

1. 恢复 Structure 中的真实结构。
2. 作为 Algorithm 的独立输入。

第二种用途不会改变 Structure。

## 9. Client Workbench

客户端只有一个工作区。

工作区提供两个互斥模式：

```text
Structure
Algorithm
```

### 9.1 Structure 模式

负责：

- 结构导航
- 结构操作
- 结构可视化
- Snapshot 保存/恢复
- Structure History

Structure 是唯一可编辑的领域状态。

### 9.2 Algorithm 模式

负责：

- 算法导航
- 参数配置
- Snapshot 输入选择
- 算法执行
- live pause/resume/step
- Timeline replay
- Log / Statistics

进入 Algorithm 后，输入来源会明确显示。

算法从当前结构 Snapshot 或保存 Snapshot 创建独立临时输入，不修改 Structure。

Structure-only 模块不会显示算法执行入口。

### 9.3 运行期状态

算法运行期间工作区模式和模块导航保持锁定，避免共享可视区域出现状态交叉。

运行结束后恢复导航。

### 9.4 Maze

Maze 生成算法的输出先作为算法结果展示。需要显式应用结果，才会写入 Structure。

Maze 寻路可以读取当前 Maze Snapshot 或已保存 Snapshot。

## 10. Playback 与 Replay

Client 使用有序 playback queue 消费 EventEnvelope。

```text
EventEnvelope
    ↓
JavaFxEventSink
    ↓
Reducer
    ↓
immutable ViewState
    ↓
Visualizer
```

Reducer 和 ViewState 都属于 presentation 层。

算法 worker 不等待动画延迟。

两个完成状态具有不同含义：

- `runtimeCompletion`：算法/结构执行结束。
- `presentationCompletion`：实时动画播放结束。

执行完成后，保存的 EventEnvelope 可通过 Timeline 做 backward / forward / seek / replay。

## 11. Statistics 与 Logging

Statistics 根据 EventEnvelope 计算：

- total event count
- domain event count
- lifecycle event count
- domain metrics
- event span
- runtime duration

visual frame 和 playback duration 属于 Client 展示信息。

领域代码可以直接使用：

```java
Log.d(...);
Log.i(...);
Log.w(...);
Log.e(...);
```

日志通过 `LogEvent` 进入统一事件流。

## 12. Server 架构

请求执行链：

```text
HTTP Request
    ↓
AlgorithmsController
    ↓
AlgorithmExecutionService
    ↓
ModuleRegistry
    ↓
ExecutionScheduler
    ↓
ExecutionRuntime
    ↓
RecordingEventSink
```

HTTP DTO 只存在于 Server 边界。Service 将 DTO 转换为领域输入后调用具体算法方法。

## 13. 扩展流程

### 新增数据结构

1. 定义结构契约。
2. 实现真实结构。
3. 定义必要的结构事件。
4. 增加 Snapshot 数据类型（如需要）。
5. 注册 `structure.*` key。
6. 在 Client 增加结构操作和 Visualizer。

### 新增算法

1. 定义领域方法和输入输出。
2. 实现算法逻辑。
3. 定义必要的语义事件。
4. 注册 `algorithm.*` key。
5. 在 Client 增加 reducer / visualizer（如需可视化）。
6. 在 Server 增加 DTO 转换（如需 HTTP 调用）。

## 14. 设计约束

- core 保持 UI 无关。
- 算法和数据结构保留明确的领域语义。
- Event 表达领域事实，不表达颜色或动画时长。
- Snapshot 不保存 ViewState。
- Runtime 管理执行，不实现算法。
- Client 管理 presentation，不修改算法内部状态。
- Server DTO 不进入 core。
- 执行线程统一由 ExecutionScheduler 管理。
