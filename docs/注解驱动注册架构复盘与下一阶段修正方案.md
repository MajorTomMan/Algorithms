# 注解驱动注册架构复盘与下一阶段修正方案

基线：`dev@c09ba913057209fe3199e2264518be97514f37e3`

本方案用于记录当前“注解驱动注册 + 动态 ValueType + 通用 Structure 可视化”架构的最终边界，并作为下一阶段代码改造的正式约束。

本轮不再继续扩张抽象层。核心目标已经收敛为：

> Algorithm / Practice 负责产生和解释数据；Structure 负责保存结构事实；Event 负责记录事实；Visualizer 负责忠实展示事实。

同时保持：

> 值类型可以动态变化，结构拓扑保持稳定；算法语义不得渗入 Structure / Event / Visualizer。

## 1. 当前状态判断

当前主方向成立，不需要回退旧 `ModuleRegistry / ModuleLoader / algorithms.factories / ServiceLoader` 体系。

已经完成并应继续保留：

- Structure 使用 `@Structure` 固定包扫描与自动发现。
- Algorithm 使用 `@Algorithm` 固定包扫描与自动发现。
- `AlgorithmDescriptor / StructureDescriptor / ComponentRegistry / StructureResolver` 已成为正式注册主链。
- `AlgorithmKey(moduleId, valueType, algorithmId)` 已取代全局 Algorithm ID 唯一模型。
- 同一 `module + algorithm id` 可以同时存在不同 ValueType 实现。
- StructureResolver 已支持 Contract 唯一实现解析，以及多实现时通过 `structureId` 显式选择。
- `Array<T>`、`LinkedList<T>`、`Tree<T>`、`Graph<T>`、`WeightedGraph<T>` 等 Structure 已具备泛型基础。
- `VisualValue` 已使 Array / Linked / Tree / Graph 的 ViewState / Reducer / Visualizer 主链摆脱 `Integer` 绑定。
- GridMaze 保持领域对象，不伪造 `MazeStructure<Boolean>`。
- Practice 已具备 `@Problem / @ProblemEntry / ProblemDiscovery / Worker JVM / JDI factual recording` 基础运行链。

因此下一阶段不再重新设计 Registry / Resolver，而是完成两个剩余目标：

```text
1. Structure 高性能 bulk initialization
2. Workbench / Structure Visualization 的 runtime ValueType 泛化
```

## 2. Algorithm Identity 已完成收口

Algorithm 的正式身份为：

```text
moduleId + valueType + algorithmId
```

例如以下注册应同时合法存在：

```text
(array, Integer, insertion-sort)
(array, String, insertion-sort)
```

Algorithm 名称不编码类型：

```text
insertion-sort        ✓
string-insertion-sort ✗ 仅为了区分 ValueType
```

正式查询入口应保持：

```java
requireAlgorithm(moduleId, valueType, algorithmId)
findAlgorithm(moduleId, valueType, algorithmId)
algorithms(moduleId, valueType)
```

不恢复全局 `requireAlgorithm(String id)` 这种有歧义的核心入口。

---

## 3. module 与 structure 的正式语义

两者继续保持独立：

```text
module
= Workbench / Algorithm Catalog 的逻辑分组

structure
= Runtime 所要求的 Structure Contract
```

例如：

```text
Kruskal
module    = graph
structure = WeightedGraphStructure
```

Maze：

```text
module    = maze
structure = none / Void.class
```

不规定：

```text
module == structure id
```

也不根据 Structure Contract 自动推导 module。

## 4. StructureResolver 保持当前边界

Resolver 的正式规则：

```text
0 个候选 -> error
1 个候选 -> return
多个候选 -> 必须显式 structureId
```

保留：

```java
resolve(contract)
resolve(contract, structureId)
create(contract)
create(contract, structureId)
```

当前不增加：

- priority
- default=true
- profile
- performance score
- 自动 benchmark 选择
- DI qualifier

多实现存在时显式选择，不做隐式猜测。

## 5. 核心职责边界

### 5.1 Algorithm / Practice

Algorithm / Practice 负责：

- 构造自身需要的输入数据。
- 保证传给 Structure bulk initialization 的数据满足目标 Structure Contract 的前置条件。
- 检查算法自己的前置条件。
- 解释业务语义和算法语义。
- 允许具体类型实现，不强迫全部算法泛型化。

例如以下都允许长期存在：

```text
IntegerInsertionSort
StringInsertionSort
CityAStar
```

算法是否应该抽成 `<T>` 由算法本身决定，而不是框架强制。

### 5.2 Structure

Structure 是泛型事实容器：

```text
Array<T>
LinkedList<T>
Tree<T>
Graph<T>
WeightedGraph<T>
```

Structure 负责：

- 保存合法的结构事实。
- 维护普通 mutation API 的自身结构语义。
- 提供高性能 bulk initialization 入口。
- 忠实保存调用方给出的值和拓扑。

Structure 不负责：

- 判断算法算得对不对。
- 判断业务数据是否符合现实。
- 为某个 Algorithm 修正输入。
- 自动补数据、去重、排序、转换或猜测调用方意图。

例如：

```text
北京 -> 上海 weight = 1
```

只要调用方把它作为受信任输入交给 Structure，Structure 不应因为“现实上不合理”而修改它。

同理，某种数据是否适合 Dijkstra、A*、Counting Sort 等，是 Algorithm 自己的前置条件问题，不进入通用 Structure 语义。

### 5.3 Event

Event 继续保持：

```text
factual
algorithm-agnostic
structure-oriented
```

不得增加算法特化 Event。

Event 只记录真正发生的执行事实，不解释算法意义，也不判断正确性。

### 5.4 Visualization

Visualizer 的原则固定为：

> Structure 当前是什么样，就忠实画成什么样。

Visualizer 不：

- 判断算法对错。
- 修正错误值。
- 根据算法名称猜测语义。
- 根据 ValueType 写特殊算法逻辑。

## 6. Structure bulk initialization

### 6.1 目标

Structure 需要一条与普通 mutation API 不同的高性能初始化通道，用于：

- Algorithm 生成大型初始数据。
- Practice 生成测试输入。
- 文件 / 数据库加载大型数据集。
- 一次性构造大规模 Graph / Tree / Array / Linked 等结构。

典型流程：

```text
Algorithm / Practice / Loader
        ↓
构造合法输入
        ↓
structure.initialize(...)
        ↓
Structure 直接批量建立内部状态
        ↓
ready
```

### 6.2 trusted bulk-load 语义

`initialize(...)` 是受信任的快速装载入口。

调用方负责保证输入满足目标 Structure Contract 的要求；违反前置条件属于调用方 Bug。

Structure 不建立一套昂贵的通用预校验流程，也不需要：

```text
validateEntireGraph(...)
validateEntireTree(...)
GenericStructureValidator
```

实现可以在无法继续构造时自然 fail-fast，但不为所有可能的自定义 Structure 建立中心化验证框架。

### 6.3 不统一初始化数据模型

框架不定义：

```text
Initializable<I>
UniversalStructureData
StructureFactory
通用 Init DTO
```

每个 Structure Contract 自己定义最自然的 bulk 输入形状。

优先使用 Java 自身数据结构：

```text
List
Collection
Map
Set
```

只有在 JDK Collection 无法清晰表达结构语义时，才允许该 Structure 定义自己的轻量 input record。

例如可以是：

```text
Array / Linked
    List<T> / Collection<T>

Graph
    Map<T, Collection<T>>

WeightedGraph
    Map<T, Map<T, Double>>
```

Tree 或未来自定义 Structure 可以自行决定更合适的输入形式。

框架不理解这些输入格式，也不参与解析。

### 6.4 bulk initialization 不伪造 mutation Event

初始化不是算法执行过程。

因此：

```text
initialize([1, 2, 3])
```

不应伪造成：

```text
insert(1)
insert(2)
insert(3)
```

大型 Graph 初始化也不应生成几十万条 `addVertex / addEdge` Event。

正确语义是：

```text
initial state
    ↓
Algorithm Run
    ↓
真实 mutation / observation Event
```

Timeline 从已经构造好的 initial state 开始记录执行事实。

### 6.5 bulk path 可以直接构造内部表示

Bulk API 的价值不仅是减少 Java 方法调用，而是跳过普通 mutation 路径中的：

- 重复查找。
- 单条合法性检查。
- 每次扩容。
- Event 生成。
- 单条拓扑维护成本。

例如当前 Graph 普通 `addEdge()` 需要查找已有 Edge；大规模数据通过逐条 API 导入可能产生明显额外成本。

Bulk path 应允许 Structure 根据输入规模直接：

```text
预分配
建立 Vertex
建立 adjacency
建立 Edge
建立 weight index
```

从而尽可能接近 `O(V + E)` 构造。

## 7. Runtime ValueType 泛化

### 7.1 泛化目标

目标不是让所有 JavaFX Controller 都变成：

```java
Controller<T>
```

而是让同一个 Structure Visualization 能承载不同 runtime ValueType：

```text
Array<Integer>
Array<String>
Array<CustomValue>

Tree<Integer>
Tree<String>
Tree<CustomValue>

Graph<Integer>
Graph<String>
Graph<City>
```

并复用同一套：

```text
Structure
Event
Reducer
ViewState
Visualizer
```

### 7.2 当前已泛化层

当前已经成立：

```text
StructureEvent factual value
        ↓
Reducer
        ↓
VisualValue
        ↓
ViewState
        ↓
Visualizer
        ↓
Timeline / Replay
```

因此下一步主要处理 Controller / 输入编辑 / Snapshot 的 ValueType 边界。

### 7.3 Visualizer 不直接读取 Annotation

Visualizer 不读取：

```java
@Algorithm(type = ...)
```

Annotation 只在 Discovery 阶段进入 Descriptor：

```text
@Algorithm
    ↓
AlgorithmDescriptor.valueType
    ↓
Runtime / Controller
    ↓
Structure<T>
    ↓
Event / VisualValue
    ↓
Visualizer
```

Visualizer 只消费结构拓扑和展示值。

### 7.4 不兼容 ValueType 直接失败

不做隐式转换。

例如：

```text
当前 Graph<String>
算法要求 Graph<City>
```

直接报告：

```text
value type mismatch
```

不得自动把：

```text
"Tokyo"
```

猜测转换为：

```text
City(...)
```

### 7.5 Snapshot 需要记录 ValueType

一旦同一 Structure Family 可以承载多种 ValueType，Snapshot 必须能够区分：

```text
Array<Integer>
Array<String>
Graph<City>
```

ValueType 属于数据语义，不属于 UI 设置，因此允许进入 Snapshot metadata。

字体、颜色、界面布局等仍不得进入 Snapshot / Replay。

## 8. Value Adapter / Codec 的边界

ValueType 动态化不意味着 Structure 负责字符串解析。

只有 Workbench UI 真正需要把文本输入转换成运行时对象时，才增加轻量 Value Adapter / Codec，例如：

```java
public interface ValueAdapter<T> {
    Class<T> type();
    T parse(String text);
    String format(T value);
}
```

该能力属于 client/runtime 输入边界，不属于 Structure core。

随机值生成也不强制放进统一接口；并不是所有自定义类型都天然支持随机生成。

不要在 Controller 中持续堆：

```text
if Integer
else if String
else if Long
...
```

但也不要为了 ValueAdapter 再建立一套注解扫描框架。

只验证：

还不足以证明架构真正泛化。

最终应增加至少一个普通业务对象作为验收，例如：

public record City(
        String name,

验证：

```text

```

能够复用现有：

```text

```

不要求为了该验收立即实现 A* 或路线规划算法。

此测试的目的只是证明：

> 可视化基础设施依赖结构事实，而不是 Integer/String 特例。

## 10. WeightedGraph 的类型边界

继续保持：

```java
WeightedGraph<T>
```

其中：

```text
T      = Vertex value
weight = numeric graph fact
```

不为了未来业务场景改成：

```java
WeightedGraph<T, W>
```

权重如何计算属于具体 Algorithm / Practice 的事情，与本轮 Structure / Visualization 泛化无关。

Structure 只忠实保存最终提供给它的 weight。

## 11. Maze 保持当前策略

GridMaze 继续排除在：

```text
泛型 Structure + ValueType + StructureResolver
```

体系之外。

Maze Algorithm 可以继续 Annotation Discovery，但 `structure` 使用默认 `Void.class`。

原则保持：

- Maze 不注册虚假的 `MazeStructure<Boolean>`。
- `StructureResolver.resolve(mazeDescriptor)` 必须 fail-fast。
- 不为了统一增加 INPUT/OUTPUT binding、role、DomainStructure 等模型。

## 12. Practice 边界

Practice 保持：

```text
真实执行
JDI 只记录事实
错误状态忠实保留
超时只杀 Worker
Host 不被用户代码拖死
```

Practice 可以生成具体类型数据并通过 Structure bulk initialization 建立初始结构，但不要求 Practice 自身变成通用 Structure 框架。

LeetCode / Practice 的题目签名允许保持具体类型。

## 17. 最终目标架构

```text
@Structure / @Algorithm
        ↓
Fixed Package Discovery
        ↓
Descriptor
        ↓
ComponentRegistry
        │
        ├── StructureDescriptor
        │
        └── AlgorithmKey(module, valueType, id)
                    ↓
              StructureResolver
                    ↓
             Structure<T>
                    ↑
                    │ trusted bulk initialize
                    │
          Algorithm / Practice
                    │
                    ↓
              Algorithm Run
                    ↓
       factual Event / Observation
                    ↓
          Timeline / Replay
                    ↓
             Reducer / ViewState
                    ↓
               VisualValue
                    ↓
               Visualizer
```

最终原则固定为：

> Algorithm / Practice 负责构造和解释数据；Structure 负责高效保存结构事实；Event 负责记录事实；Visualizer 负责忠实展示事实。

> Structure 可以接受业务上错误、算法上错误但调用方认为合法的输入，不负责纠错；违反 bulk initialization 前置条件属于调用方 Bug。

> ValueType 是 Algorithm identity 和 Runtime Structure 的独立维度；不兼容直接失败，不做隐式转换。

> Structure 拓扑决定可视化形态，ValueType 不决定 Visualizer 实现。`Graph<Integer>`、`Graph<String>`、`Graph<City>` 应复用同一套 Graph Visualization。

> 算法语义不得进入 Structure / Event / Visualizer。
