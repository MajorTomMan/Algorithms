# 注解驱动注册架构复盘与下一阶段修正方案

基线：`dev@50557d1af50a2445ded0ae3a8a2e79a8e8a67b0b`

本方案用于复盘当前“注解驱动注册与动态类型”改造的实际落地状态，并明确下一轮需要优先修正的架构问题。目标不是再次推翻现有实现，而是在现有 `Annotation -> Discovery -> Descriptor -> Registry -> Resolver` 主链已经成立的基础上，修正 Algorithm identity、module 语义和 StructureResolver 的扩展边界，再继续推进 Workbench 的动态 ValueType。

---

## 1. 当前状态判断

当前主方向成立，可以继续沿现有架构演进，不需要回退旧 `ModuleRegistry / ModuleLoader / algorithms.factories / ServiceLoader` 体系。

已经完成并可以保留的部分：

- Structure 使用 `@Structure` 固定包扫描与自动发现。
- Algorithm 使用 `@Algorithm` 固定包扫描与自动发现。
- `AlgorithmDescriptor / StructureDescriptor / ComponentRegistry / StructureResolver` 已成为正式注册主链。
- 旧 factories、旧 ModuleDiscovery、类名推导算法 ID 的逻辑已退出。
- `Array<T>` 等泛型 Structure 已经可以作为多 ValueType 的共用底层实现。
- `VisualValue` 已使 Array / Linked / Tree / Graph 的 ViewState / Reducer / Visualizer 主链摆脱 `Integer` 值类型绑定。
- GridMaze 保持领域对象，不伪造 `MazeStructure<Boolean>`，Maze Algorithm 可以注解发现但不进入 `StructureResolver`。
- Practice 已具备 `@Problem / @ProblemEntry / ProblemDiscovery / Worker JVM / JDI factual recording` 的基础运行链。

当前真正需要优先处理的不是 Event、Timeline、Snapshot 或 Visualizer，而是 Registry 的身份模型和 Resolver 的选择模型。

## 2. P0：修正 Algorithm Identity

### 2.1 当前问题

当前 `ComponentRegistry` 使用：

```java
Map<String, AlgorithmDescriptor> algorithmsById;
```

并要求：

```text
Algorithm id 全局唯一
```

这会导致同一种算法在不同 ValueType 下必须人为改 ID，例如：

```text
insertion-sort
string-insertion-sort
long-insertion-sort
```

这与本次改造的目标冲突，因为 `type` 已经是 AlgorithmDescriptor 的独立信息。如果最终仍把类型编码进 `id`，等于重新把旧 Registry key 的问题带回来。

### 2.2 目标模型

Algorithm 的唯一身份应至少由以下三部分组成：

```text
module + valueType + id
```

建议新增：

```java
public record AlgorithmKey(
        String moduleId,
        Class<?> valueType,
        String id
) {
}
```

Registry 改为：

```java
Map<AlgorithmKey, AlgorithmDescriptor> algorithms;
```

于是允许：

```java
@Algorithm(
        id = "insertion-sort",
        module = "array",
        type = Integer.class,
        structure = ArrayStructure.class
)
public final class IntegerInsertionSort implements Sort<Integer> {
}
```

以及：

```java
@Algorithm(
        id = "insertion-sort",
        module = "array",
        type = String.class,
        structure = ArrayStructure.class
)
public final class StringInsertionSort implements Sort<String> {
}
```

同时注册。

### 2.3 Registry API

推荐提供明确 API：

```java
AlgorithmDescriptor requireAlgorithm(
        String moduleId,
        Class<?> valueType,
        String id);
```

```java
Optional<AlgorithmDescriptor> findAlgorithm(
        String moduleId,
        Class<?> valueType,
        String id);
```

```java
List<AlgorithmDescriptor> algorithms(
        String moduleId,
        Class<?> valueType);
```

不建议继续保留这种有歧义的核心入口：

```java
requireAlgorithm(String id)
```

如果为了迁移临时保留，只允许在候选唯一时成功；存在多个同 ID Algorithm 时必须 fail-fast，而不能随意选择一个。

### 2.4 唯一性规则

新的唯一性应该是：

```text
(moduleId, valueType, id) 唯一
```

而不是：

```text
id 全局唯一
```

以下情况合法：

```text
(array, Integer, insertion-sort)
(array, String, insertion-sort)
```

以下情况非法：

```text
(array, Integer, insertion-sort) -> A
(array, Integer, insertion-sort) -> B
```

### 2.5 P0 验收

必须新增测试覆盖：

```text
Integer/String 同名算法可以同时注册
同 module + 同 type + 同 id 冲突 fail-fast
requireAlgorithm(module, type, id) 返回准确实现
旧 string-insertion-sort POC 可以改回 insertion-sort
AlgorithmCatalog 在不同 ValueType 下能看到相同稳定 algorithm id
```

该阶段建议在继续大规模 Workbench ValueType 动态化之前完成。

## 3. P1：明确 `module` 与 `structure` 的语义边界

### 3.1 当前问题

当前 Algorithm 注解包含：

```java
@Algorithm(
        id = "...",
        module = "...",
        type = ...,
        structure = ...
)
```

其中：

```text
module
structure
```

是两份独立 metadata。

如果没有明确语义，很容易产生：

```java
@Algorithm(
        id = "foo",
        module = "tree",
        type = Integer.class,
        structure = ArrayStructure.class
)
```

这种“注解合法、语义错误”的声明。

### 3.2 推荐定义

明确约定：

```text
module
= Workbench / Algorithm Catalog 的逻辑分组

structure
= Runtime 所要求的 Structure Contract
```

二者不是同一个概念，也不要求一一对应。

例如：

```text
Kruskal
module    = graph
structure = WeightedGraphStructure
```

这是合法且合理的。

Maze：

```text
module    = maze
structure = none / Void.class
```

也是合法的，因为 GridMaze 不进入本轮 StructureResolver。

### 3.3 不要做的事情

不要强行规定：

```text
module == structure id
```

也不要尝试仅根据 Structure Contract 自动推导 Workbench module。

原因是：

- `WeightedGraphStructure` 仍属于 graph Workbench。
- Tree 下可能存在 General/Binary/Search/AVL 等不同 Contract。
- Maze 明确没有 StructureResolver Contract。

### 3.4 校验策略

第一阶段不建议建立复杂的 module/contract 映射表。

只需要：

- `module` 必须为稳定 kebab-case。
- `structure != Void.class` 时必须是 interface。
- implementation 必须真实使用声明的 structure contract。
- 文档和测试明确 `module` 是逻辑分组而不是 Structure identity。

后续如果出现大量误配，再考虑引入轻量 `ModuleDefinition` 校验，不提前设计。

## 4. P1：StructureResolver 从“唯一实现解析器”演进为“可选择实现解析器”

### 4.1 当前行为

当前 Resolver 对一个 Contract：

```text
0 个候选 -> error
1 个候选 -> return
多个候选 -> ambiguous error
```

这对当前只有一个默认实现的情况是正确的，但还不能实现最初设想的“同一 Structure Contract 下切换不同底层实现”。

### 4.2 不需要立即做复杂策略系统

目前不要增加：

- priority 注解
- profile
- performance score
- DI qualifier
- 自动 benchmark 选择

这些都属于过度设计。

### 4.3 推荐最小扩展

保留：

```java
StructureDescriptor resolve(Class<?> contract)
```

语义：

```text
只有一个候选时直接返回；
多个候选且没有明确默认项时 fail-fast。
```

新增显式选择：

```java
StructureDescriptor resolve(
        Class<?> contract,
        String structureId);
```

以及：

```java
<S> S create(
        Class<S> contract,
        String structureId);
```

这样以后：

```text
ArrayStructure
├── array
└── compact-array
```

Algorithm 仍然只声明：

```java
structure = ArrayStructure.class
```

而 Runtime / UI 在真正需要切换实现时明确选择：

```text
array
compact-array
```

Algorithm 不依赖具体实现。

### 4.4 默认实现

当前阶段不需要新增 `default=true` 注解。

如果未来同一 Contract 确实长期存在多个实现，再评估是否需要：

```java
@Structure(..., defaultImplementation = true)
```

第一版继续保持“多实现必须显式选择”更加安全。

## 5. P2：Workbench 动态 ValueType 的真实完成边界

### 5.1 已完成

以下层已经具备动态 ValueType 基础：

```text
StructureEvent factual value
        ↓
Reducer
        ↓
VisualValue
        ↓
ViewState
        ↓
Visualizer
        ↓
Timeline / Replay
```

Array / Linked / Tree / Graph 已不需要因为 `String / Long / Integer` 修改 Event Contract 或重新写 Visualizer 拓扑逻辑。

### 5.2 尚未完成

Controller 层仍然大量是 Integer 业务边界，例如：

```text
Array<Integer>
SequenceSnapshot<Integer>
List<Integer>
parseInteger(...)
Sort<Integer>
```

因此当前状态应定义为：

> Runtime / Replay / ViewState / Visualizer 已动态化；Workbench 编辑和执行入口仍以 Integer 为主。

这不是 Bug，不需要现在推翻 Controller。

### 5.3 下一阶段推荐顺序

先完成 P0 AlgorithmKey，再做 Array Workbench 的真实动态 ValueType。

推荐只先支持：

```text
Integer
String
```

执行流程：

```text
MainController valueType
        ↓
AlgorithmCatalog(module, valueType)
        ↓
AlgorithmDescriptor(module, valueType, id)
        ↓
ValueCodec / Parser
        ↓
Array<?> runtime source
        ↓
Algorithm
        ↓
同一套 Event / Reducer / Visualizer
```

### 5.4 ValueCodec

当 Controller 真正动态化时，建议新增一个很小的值处理抽象，例如：

```java
public interface ValueCodec<T> {
    Class<T> type();
    T parse(String text);
    String format(T value);
    T random(java.util.Random random);
}
```

先提供：

```text
IntegerValueCodec
StringValueCodec
```

不要在 `ArrayController` 里继续堆：

```text
if Integer
else if String
else if Long
```

也不要让 Structure 自己负责字符串解析。

## 6. Maze 保持当前策略

GridMaze 继续排除在：

```text
泛型 Structure + ValueType + StructureResolver
```

体系之外。

Maze Algorithm 可以继续：

```java
@Algorithm(
        id = "maze-pathfinder-astar",
        module = "maze",
        type = Boolean.class
)
```

其中 `structure` 使用默认 `Void.class`。

原则：

- Maze 仍由 Annotation Discovery 注册。
- Maze 不注册虚假的 `MazeStructure<Boolean>`。
- `StructureResolver.resolve(mazeDescriptor)` 必须 fail-fast。
- Maze probe 保证注册重构不破坏原功能。
- 不为了统一增加 INPUT/OUTPUT binding、role、DomainStructure 等模型。

## 7. Practice 后续边界

当前 Practice 要求一个 `@Problem` 恰好有一个 `@ProblemEntry`，这对第一版可接受。

未来如果需要同一题多实现，例如：

```text
brute-force
optimized
dp
```

再扩展：

```java
@ProblemEntry("optimized")
```

以及：

```text
ProblemDescriptor -> List<ProblemEntryDescriptor>
```

当前阶段不要因为可能存在多解法而提前改 Worker/JDI 主链。

Practice Worker 的核心边界继续保持：

```text
真实执行
JDI 只记录事实
错误状态忠实保留
超时只杀 Worker
Host 不被用户代码拖死
```

## 8. Server 边界

Server 当前可以继续：

```text
稳定 Algorithm identity
+
显式 Transport metadata
```

Server 的 request/output DTO 不需要为了 Registry 动态化而同时改成通用 schema。

下一轮只需跟随 AlgorithmKey API 调整算法查找方式。

不要在本阶段引入：

- 动态 REST schema
- 任意类型 JSON codec 注册框架
- 自动生成 API request DTO

这些与 Registry identity 修正无关。

## 11. 明确不做

下一轮仍然不做：

- 外部 JAR / 插件系统。
- Annotation Processor。
- Spring/DI Container。
- 算法强制泛型化。
- `UniversalStructure`。

## 12. 最终目标

调整后的主链应为：

```text
@Structure / @Algorithm
        ↓
Fixed Package Discovery
        ↓
Descriptor
        ↓
ComponentRegistry
        │
        ├── StructureKey / StructureDescriptor
        │
        └── AlgorithmKey(module, valueType, id)
                    ↓
              StructureResolver
                    ↓
            Runtime Structure
                    ↓
              Algorithm Run
                    ↓
       factual Event / Observation
                    ↓
          Timeline / Replay
                    ↓
        generic Value projection
                    ↓
              Visualizer
```

最终原则：

> Algorithm 的名字不编码数据类型；`valueType` 是独立维度。`module` 负责 Workbench 分组，`structure` 负责 Runtime Contract，二者职责不同。StructureResolver 负责 Contract 到实现的解析，但在多个实现存在时必须显式选择，不做隐式猜测。Event / Timeline / Snapshot / Visualizer 继续保持算法无关和事实驱动。
